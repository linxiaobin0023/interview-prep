面试准备 — 跨越速运 AI 中台

面试开场白（1分钟版）：
"我在跨越速运负责 AI 中台，过去一年半从 0 到 1 搭建了 5 个递进项目。第一个是实时语音客服，日均处理 4 万通来电，首字延迟从 15 秒压到 2 秒，做了全链路容灾——供应商凌晨故障时 200 多通电话零感知切换规则兜底。第二个发现通用模型不懂物流术语，做了领域微调，RAG 检索命中率从 72% 提到 89%。第三个把重复建设的基础能力抽成 MCP 共享集群，新业务接入从 8 周缩到 2 天。第四个是跨境合规单证中台，用 LangGraph 编排七步流程，退单率从 15% 降到 5% 以下，60% 缺失单证自动补全。最后搭了一套 Agent Harness 工程框架，把 Agent 开发周期从 2 周压缩到 3 天，用质量红线保证上线不崩。整体是一个从场景到平台的演进路径。"
面试开场白（3~5分钟版）：
"我在跨越速运负责 AI 中台建设，可以总结成一句话：从一个具体的物流客服场景切入，逐步建设出一套 AI 基础服务平台。整个过程是五个递进的阶段，每个阶段解决不同层级的问题。

第一个阶段是 P1，实时语音智能客服。跨越速运每天有几万通客户来电，其中 60% 到 70% 都是查轨迹、问时效这类简单问题，非常适合 AI 自动化。我设计了一个五层架构：RTC 层做语音采集和传输，对话引擎用状态机加 LLM 混合架构来管流程和话术，RAG 层做知识检索，缓存优化层压延迟，工具层对接内部的轨迹查询和改派系统。流程上客户说完话，ASR 转文本，状态机判断当前阶段，LLM 理解意图，RAG 检索知识，调用业务工具，生成回复，TTS 播报。上线过程中踩过几个大坑：首字延迟一开始要 15 秒，后来发现是每次对话的 System Prompt 和 RAG 结果都要重新编码，做了 Prefix Caching 和 KV Cache 合并，压到了 2 秒以内。物流专有名词 ASR 识别率低，做了热词表优化。弱网环境下语音断断续续，加了 FEC 前向纠错和自适应 Jitter Buffer。还有一个是上线初期 LLM 供应商偶发超时，导致客服完全不可用，后来设计了全链路容灾——LLM 层挂了走规则模板兜底，覆盖 80% 高频意图；RAG 挂了走缓存兜底；RTC 层挂了自动播预录提示并转人工。有一次凌晨供应商未通知升级，连续报错触发熔断，系统自动切换规则模板，那 200 多通来电全部正常服务，没有一个客户听到错误提示。另外模型效果会随时间衰减，我们建了一套数据飞轮，badcase 自动打标、人工归类、进入优化队列、回归测试、5% 灰度发布，意图覆盖率每月能提升 2 到 3 个百分点。

第二个阶段是 P2，领域微调。P1 上线后发现通用大模型在物流领域效果不好，客户说'我的货在分拨中心停了两天'，模型根本不知道'分拨中心'是什么。所以我们做了三个方向的微调：对话模型微调让模型学会客服话术风格，Embedding 微调提升 RAG 检索准确率，意图分类微调让轻量模型快速识别意图。训练流程是两阶段，先做 SFT 学习风格，再做 DPO 学习质量排序。数据清洗是个坑，原始 1000 多条数据过滤完只剩 200 多条，后来改用 LLM 多维度评分加人工抽检，在质量和数量之间找到了平衡。最终 Embedding 命中率从 72% 提到 89%，对话模型评分从 3.5 分提到 4.2 分。

第三个阶段是 P3，MCP 共享服务集群。做了前两个项目之后，发现公司内部多个业务线都在重复建设 LLM 网关、RAG 检索、会话记忆这些基础能力。我们用 MCP 协议把它们抽成了四个共享 Server：LLM 网关管模型路由和限流，RAG 检索管知识库，会话记忆管对话上下文，Prompt 模板管提示词版本。业务 Agent 发请求到 REST-MCP 网关做鉴权和转换，再路由到对应 MCP Server。多租户隔离是个博弈点，业务团队要求完全隔离，但成本太高，最后做了逻辑隔离——RAG 用 Collection 前缀，记忆用 user_id 加 project_id，底层物理存储共享。效果很明显，新业务接入周期从 8 周压缩到 2 天。

第四个阶段是 P4，跨境合规与单证中台。跨越做 200 多个国家的跨境业务，每票货要准备 5 到 8 份单证，人工审要 3 到 5 天，退单率 15%。我设计了一个七步流程：单据解析、多源比对、合规审查、缺失项识别、自动补单或人工复核、通关放行、复盘。技术上有三个关键设计：第一是多源单据统一解析，纸质面单走 OCR、Excel 做列映射、PDF 做版面分析，最终统一输出 Pydantic Schema，后面的节点不用关心原始格式。第二是合规审查用 Drools 规则引擎管硬规则，LLM 管软规则，最终决策权在规则引擎，LLM 只打标签提示风险，防止幻觉导致放行不合规货物。第三是合规审查经常跨天，用 PostgreSQL Checkpointer 做持久化，支持 interrupt 和 resume 人工复核，服务重启也不丢状态。效果上，简单 case 现在 1 天内自动放行，退单率从 15% 降到 5% 以下，60% 的缺失单证能自动补全。

第五个阶段是 P5，Agent Harness 工程框架。前面四个项目做下来，发现团队开发 Agent 没有标准流程，Prompt 散落在代码里，上线后效果崩了不知道哪里出问题。所以设计了五阶段流程：Intent Spec 把业务需求结构化，Design Review 确保方案合理，Implementation 写代码，Verification 跑评测集过质量红线，Feedback Loop 收集线上数据迭代。质量红线一开始是单项必须过，结果一个边界 case 波动就阻断发布，后来改成总分加权，允许个别 case 有波动。评测集每月更新 30%，用线上真实样本替换老 case，防止 Prompt 过拟合。上线后 Agent 开发周期从 2 周压缩到 3 天，新人上手也从 2 周缩短到 3 天。

总结来看，这五个项目形成了'从场景到平台'的完整闭环：P1 落地第一个 AI 场景证明价值，P2 解决模型不够懂业务的问题，P3 把重复能力抽象为共享服务，P4 证明复杂工作流也能用 AI 编排，P5 最后把工程化方法论沉淀下来。"

Q1: 在跨越速运的语音客服项目中，为什么选火山引擎RTC来做ASR和TTS？⭐⭐▶

说实话当时主要考虑了三个方面。第一是接入成本，火山引擎把ASR和TTS打包在一个SDK里，我们不用分别对接两家的服务，语音链路的联调周期直接缩短了一半。第二是我们已经在用它的ARK API跑豆包大模型了，整个生态是通的，不用再维护另一套供应商的账号和鉴权。第三是声音复刻能力，我们做客服希望声音有品牌辨识度，火山这块比阿里云和腾讯云都成熟一些。

→ ASR准确率多少？有没有做领域词表优化？

通用场景准确率大概95%左右，但物流专有名词比如"分拨中心"、"干线运输"这些一开始识别得不太好。我们做了一个物流领域的热词表喂给ASR，准确率提到了97%左右。

→ 流式ASR的延迟大概是多少？

端到端大概300-500ms，用户说完一句话基本能立刻出文字。非流式的话要等用户说完整段才开始转写，延迟不可控，在语音场景下体验很差。

Q2: 你们的语音客服对话管理是怎么做的？为什么不用纯LLM？⭐⭐⭐▶

我们试过纯LLM驱动，发现两个问题。一是业务流程不可控，比如客户说"我要投诉"，纯LLM可能直接开始安慰客户而不是先创建工单。二是调试太难了，出了问题你根本不知道LLM当时在想什么。

所以最后用了一个混合架构：状态机管"做什么"，LLM管"怎么说"。比如客户来电，状态机先切到greeting状态，让LLM生成一段问候语；然后切到intent_detect，LLM识别出客户要查轨迹；状态机切到query_track，LLM调用查轨迹的Tool拿到结果，再生成自然语言回复。状态机保证流程不会乱走，LLM保证对话自然。

→ 状态机大概多少个状态？怎么管理状态膨胀？

核心状态大概15个左右，按业务域分组：通用流程（greeting/closing）、查询类（query_track/query_eta）、变更类（change_addr）、投诉类（complaint/escalate）。我们用状态表配置化管理，新增一个状态就是加一行配置，不用改代码。

→ 客户说的话状态机没覆盖怎么办？

状态机有一个兜底的"其他"状态，走LLM自由回复。如果LLM识别出确实是一个新的高频意图，我们会记录下来，下个迭代加到状态机里。这样系统的覆盖率是逐步提升的。

Q3: 语音客服刚上线的时候首字延迟15秒，用户根本等不了，你们怎么优化到2秒的？⭐⭐⭐▶

这个是当时最痛的问题。用户打客服电话，说完问题要等15秒才听到第一个字，体验极差。我们排查下来发现主要瓶颈在LLM推理，因为每次请求都要重新编码System Prompt加上RAG检索结果，token量很大。

做了几件事：第一，固定RAG检索片段的排序规则，这样相同的System Prompt前缀就能触发模型的Prefix Caching，不用每次重新编码。第二，把System Prompt里能合并的消息体合并掉，减少KV Cache的重复计算。第三，简单意图直接走doubao-lite，推理本身就快很多，不用等pro模型慢慢想。整体从15秒压到了2秒以内。

→ Prefix Caching的命中率大概多少？

因为我们的System Prompt是相对固定的，加上RAG片段排序也固定了，所以前缀命中率大概在70%-80%。每次命中能省掉大概1000个token的编码时间。

→ KV Cache和Prefix Caching的区别是什么？

KV Cache是Transformer推理时缓存已计算的Key和Value，避免同一个序列重复计算。Prefix Caching是更高层的概念，利用KV Cache的机制，把多个请求共享的前缀部分缓存起来。简单说KV Cache是底层机制，Prefix Caching是利用这个机制做的优化策略。

Q4: 语音客服的RAG检索是怎么做的？和文本场景有什么区别？⭐⭐▶

语音场景和文本场景差别挺大的。文本场景用户打了一大段话，信息量充足，检索可以很精准。但语音场景用户经常就一句话，比如"我的快递咋还没到"，信息量很少，检索难度大。

我们用了HNSW_HYBRID混合检索，同时走稠密向量和稀疏向量两条路，语义理解和关键词匹配都能兼顾。然后做了Int8量化，向量存储空间降了75%，检索速度也快了不少。还有一个专门针对语音场景的优化：我们引入了一个轻量的rerank模型做二次排序，因为语音转出来的文本经常有识别误差，直接用原始相似度排序不太靠谱，rerank能纠正一部分。

→ top-k取多少？怎么确定的？

粗召回top-20，然后rerank精排取top-5。这个是压测出来的，top-5能覆盖90%以上的场景，再多了LLM的输入token就太长了，延迟扛不住。

→ dense_weight动态平衡怎么做的？

对查轨迹这种需要精确匹配运单号的场景，调高稀疏向量的权重；对问时效这种语义理解为主的场景，调高稠密向量的权重。通过Metadata标签自动识别场景类型来动态调整。

Q5: 语音客服的简单问题和复杂问题怎么分流的？⭐⭐▶

我们在意图识别那一步就做了分流。跨越速运的客服来电大概60-70%是查轨迹、问时效这种简单问题，剩下的才是投诉、理赔这种复杂场景。

简单问题走doubao-lite，推理快、成本低，TTFT能控制在500ms以内。复杂问题走doubao-pro-256k，虽然慢一点但推理能力强，上下文窗口也大，能处理客户长篇描述的问题。路由逻辑写在意图识别模块里，在调LLM之前就决定了用哪个模型。

→ 意图识别用的什么方案？

用了一个轻量级的分类模型，不是LLM。因为意图识别这一步本身就在延迟链路上，如果用LLM做意图识别那就本末倒置了。分类模型推理时间大概50ms，够快。

→ 路由错误怎么办？有没有fallback？

有的。如果lite模型处理不了（比如回复了"我不太理解"），会自动升级到pro模型重试一次。不过实际运行下来升级率很低，大概5%左右。

Q6: 物流司机经常在信号差的地方打电话，语音断断续续的怎么处理？⭐⭐⭐▶

这个确实是个大问题。跨越速运的司机经常在高速上、仓库里打电话，网络环境很差。我们做了两层防护。

第一层是FEC前向纠错，发送端在语音数据里加入冗余信息，接收端即使丢了30%的包也能通过算法恢复出来，用户完全听不出来。第二层是自适应Jitter Buffer，根据实时网络抖动情况动态调整缓冲区大小——网络好的时候缓冲区小延迟低，网络差的时候缓冲区大一点保证连续性。两层配合起来，实测50%高丢包率下语音对话基本无感知。

→ FEC的冗余比例是多少？

我们配的是30%冗余，也就是发100个包里有30个是冗余的。这个比例是权衡的结果——再高的话延迟增加明显，再低的话恢复能力不够。30%能覆盖绝大多数弱网场景。

→ Jitter Buffer最大延迟增加多少？

正常网络下Buffer大小是20ms，基本不影响。极端弱网下会动态扩展到200ms，用户能感知到一点点延迟但语音是连续的，比断断续续好很多。

Q7: 你们做了TTS声音复刻，在物流客服场景下这个投入值得吗？⭐▶

这个一开始团队也有争议，觉得物流客服又不是直播带货，搞声音复刻是不是过度设计。但后来发现还是有价值的。跨越速运是To B的物流企业，客户都是企业客户，对服务品质要求比较高。如果客服声音一听就是机器人，客户会觉得这家公司的技术水平不行。复刻之后声音自然了很多，配合ASR的情绪感知——比如客户语气比较急躁的时候，TTS会自动调整语速和语调更温柔一些——整体客户接受度提升了不少。

→ 声音复刻训练数据需要多少？

我们录了大概2小时的高质量语音就够了。火山引擎的声音复刻对数据量要求不高，关键是发音要清晰、覆盖所有音素。我们找了一个声音辨识度比较好的客服主管录的。

→ 用户能分辨出是AI吗？

简单对话基本分辨不出来，特别是客户只是查个快递的时候。复杂场景比如投诉的时候偶尔会觉得"这个客服怎么说话有点怪"，但整体比通用TTS好很多。

Q8: 你们是怎么管理语音客服的提示词的？⭐▶

一开始就是把prompt写在代码里，改一行代码要重新部署，特别痛苦。后来我们搞了一个Prompt Pilot的管理机制。核心思路是给每个prompt配一个评测集，你改了prompt之后自动跑评测，和上一个版本的分数做对比。如果分数降了就不让你上线。还有一个挺有用的feature是负样本自动优化——对那些回复很差的case，用算法自动重构prompt里的描述，相当于自动debug。这些高质量的case也沉淀下来，后面做微调的时候直接用。

→ 评测集是怎么构建的？

两部分：一部分是人工标注的典型场景，覆盖每种意图的常见问法；另一部分是从线上日志里捞的真实对话，按满意度评分筛选出来的。大概500个case，覆盖了95%以上的场景。

→ 版本对比的具体指标是什么？

主要看四个：意图识别准确率、回复相关性评分、Token消耗量、延迟。前两个是质量指标，后两个是效率指标。四个都达标才能上线。

Q9: 语音场景的Token消耗怎么控制的？⭐⭐▶

语音场景有个特殊之处：用户说了一句话，你回复不能太长——电话里念一大段文字用户根本听不完。但推理过程可能需要很多token来理解上下文和调用工具。

所以我们做了一个Max Token分级控制。分析了历史数据，发现95%的对话输出都在200个token以内，我们就把这个作为上限。然后根据场景动态分配推理和输出的比例：查轨迹这种输出简短的场景，给推理多分配一些token，保证理解准确；投诉处理这种需要详细回复的场景，给输出多分配一些。整体下来单请求的token利用率提升了不少，成本也降了。

→ 不同场景的token比例分别是多少？

查轨迹：推理1500/输出100，因为回复就是一句话"您的快递在XX位置"。投诉处理：推理1000/输出300，因为需要详细解释处理方案。大概是这么个比例。

→ 设置过小会怎样？

输出token设太小的话，回复会被截断，用户听到一半就没声音了，体验很差。推理token设太小的话，模型可能来不及理解完整上下文就开始回复，准确率会下降。

Q10: 从用户说完到听到回复，端到端延迟现在大概多少？⭐⭐▶

简单问题走lite模型的话，大概2-3秒。复杂问题走pro模型，大概4-5秒。这个是包括ASR转写、LLM推理、TTS合成全链路的。比起之前15秒的体验已经好很多了，用户基本感觉不到明显等待。

优化思路就是把链路上每个环节都压了一遍：ASR用流式识别边说边转，不用等用户说完；LLM用Prefix Caching减少重复编码；TTS也是流式合成边生成边播放；再加上简单意图走lite模型保证低延迟。弱网环境下FEC和Jitter Buffer保证语音连续性。

→ 有没有做过优化前后的A/B测试？

做过。优化前用户平均通话时长5分钟左右，优化后降到1.5分钟——不是因为话少了，而是因为用户不用等了，对话节奏紧凑了。客户满意度评分也从3.2提升到了4.1（5分制）。

Q11: 语音客服上线后如果LLM服务挂了，客户还能正常打电话吗？你们的容灾降级是怎么设计的？⭐⭐⭐▶

设计上必须保证任何单点故障都不会让客户听到"系统错误"。我们做了分层降级策略，按依赖层级从外到内逐层兜底。

第一层是RTC层，如果ASR服务挂了，语音转不了文本，系统会播一段预录好的提示"当前信号不好，请稍后再试或转人工服务"，同时自动帮客户排队转人工。如果TTS挂了，LLM生成的文本可以通过预存的模板映射成固定语音片段播报，虽然不够自然但能保证服务不中断。

第二层是LLM层，这是最关键的一层。如果LLM推理服务超时或报错，状态机直接切换到rule_fallback状态，走规则模板回复。比如客户说"查轨迹"，LLM挂了就直接调用查轨迹接口拿到结果，用固定模板"您的快递目前在XX位置"播报，不走LLM生成。规则模板覆盖了Top-80%的高频意图，虽然回复没那么自然，但信息是准确的。

第三层是RAG层，如果向量库检索失败，直接走Redis缓存里的最近热点答案，再不行就用通用物流知识兜底——LLM基于预存的通用知识回答，不带具体时效数据，但至少不会胡说。

每一层都有熔断机制。连续5次调用失败触发熔断，30秒后半开探测，探测成功了再恢复全流量。这样即使某个服务整体挂了，也能在秒级内完成降级，客户基本无感知。

→ 规则模板覆盖80%意图，那剩下20%怎么办？

剩下的低频意图直接转人工。我们算过账，20%的低频意图如果也要用规则模板覆盖，维护成本会高很多，不如直接转人工更划算。而且低频意图往往比较复杂（比如跨境报关问题），人工处理效果更好。

→ 降级后的客户满意度会不会明显下降？

会有一定下降，但比完全不可用好得多。实测LLM降级到规则模板后，客户满意度从4.1降到3.5左右，但仍然在可接受范围。而且降级是临时性的，服务恢复后自动切回LLM模式，不需要人工干预。

→ 有没有遇到过真实的大规模故障？

有过一次。某个凌晨LLM供应商做升级，我们这边没收到通知，连续报错触发了熔断。系统自动切换到规则模板模式，那个小时大概有200多通来电走了降级链路，全部正常服务，没有一个客户听到错误提示。早上我们收到监控告警后联系供应商确认，恢复后切回LLM。这件事让我们验证了降级策略是有效的。

Q12: 语音客服上线后模型效果会不会衰减？你们怎么保证系统持续迭代？⭐⭐⭐▶

会衰减，而且衰减得比传统系统快。因为物流政策在变、产品在变、客户问法也在变，模型学的是历史数据，过几个月就可能跟不上。

我们建了一套数据飞轮来解决这个问题。核心是自动发现badcase、归类、进入对应优化队列、回归测试、灰度发布，形成闭环。

第一步是badcase自动发现。三个信号触发：客户满意度评分低于3分、对话轮数超过10轮（说明模型没理解或没解决）、客户主动说"转人工"或"找你们领导"。这些case会自动从日志里捞出来，打上badcase标签。

第二步是人工归类。运营同事每天花30分钟审这批badcase，分成几类：意图缺失（客户问了个新场景模型不认识）、RAG不准（检索结果和答案对不上）、模型幻觉（模型编了个不存在的政策）、流程bug（状态机跳转错了）、其他。每类进入不同的优化队列。

第三步是优化执行。意图缺失的→补充意图到状态机配置+收集训练数据；RAG不准的→更新知识库文档或调整检索策略；模型幻觉的→优化Prompt约束+补充负样本到评测集；流程bug的→修状态机配置。

第四步是回归测试+灰度发布。改完后先跑评测集，分数不降才允许上线。上线不是全量，先切5%流量做A/B测试，对比新旧版本的关键指标（准确率、满意度、转人工率）。指标变好了才逐步扩到100%。

效果上，这套飞轮跑起来后，意图覆盖率每月提升2-3%，badcase的闭环处理周期从2周缩短到3天。

→ 5%灰度怎么保证统计显著性？

5%流量每天大概几百通电话，跑一周积累几千个样本，对于准确率这种指标足够做显著性检验了。如果改动比较大，会提到10%跑两周。关键是看相对变化趋势，不是绝对数值。

→ 回归测试的评测集是怎么保持新鲜的？

每月更新30%。用线上捞的真实badcase替换掉老case，保证评测集反映当前业务。同时新case和Prompt里的示例做相似度检查，避免过拟合——如果评测集里的问题和Prompt示例太像，模型可能只是背答案而不是真理解。

→ 运营同事每天审badcase，如果量太大审不过来怎么办？

用LLM做预分类。badcase先过一个轻量分类模型，自动打上初步标签（意图缺失/RAG不准/幻觉/流程bug），运营同事只需要确认和修正，不需要从零分类。预分类准确率大概80%，能省掉大部分重复劳动。

Q13: 客户打电话来发火骂人，AI客服能识别出来吗？怎么处理？⭐⭐▶

能识别，而且是语音场景的天然优势——除了文本内容，还能从语音特征判断情绪。

我们做了联合情绪识别。ASR层面提取语音特征：语速突然变快、音量变大、停顿变少，这些都是愤怒的信号。LLM层面从文本理解情绪：关键词如"投诉"、"太慢了"、"什么意思"、"你们怎么搞的"，以及反问句、连续追问等语言模式。两层结果融合，输出情绪等级：平静、不满、愤怒。

不同情绪等级走不同的处理策略。平静→正常流程处理。不满→Agent的回复会带上安抚话术（"非常理解您的心情，我马上帮您查"），同时提升处理优先级，查轨迹走更快的接口。TTS的语速也会放慢、语调更柔和。愤怒→不再尝试用AI解决问题，直接播安抚话术+立即转人工，同时自动创建高优先级工单，把通话摘要推给人工客服主管，让人工做好准备再接起电话。

实际效果还不错。愤怒客户如果让AI硬扛，往往会越聊越生气，最后投诉升级。发现愤怒后立刻转人工，虽然AI没解决完问题，但客户感受到"被重视"，后续投诉率反而降低了。

→ 情绪识别的准确率怎么样？会不会误判？

整体准确率大概85%左右。误判主要集中在"不满→平静"——有些客户说话直来直去，但其实没有生气，模型会过度敏感。误判的另一端是"平静→愤怒"，这种比较少。我们允许一定的过度敏感，因为把平静客户当成不满来处理（多安抚几句）成本很低，但把愤怒客户当成平静来处理代价很高。

→ 转人工的时候客户需要重新描述问题吗？

不需要。AI会把通话摘要（客户诉求、已查到的信息、当前处理状态、客户情绪）一起推给人工，人工接起来就能直接说"您好，我了解到您反映的是XX问题，我已经看到您的快递目前在XX位置"。这个摘要也是LLM自动生成的，结构化输出。

Q1: 你们微调用的数据是怎么清洗的？为什么要做这么多步骤？⭐⭐⭐▶

原始数据质量直接决定微调效果，我们在这上面踩过坑。一开始觉得1000多条聊天记录挺多的，直接扔进去训练，结果模型学了很多废话——表情包、撤回消息、客服发错又撤回的链接，这些对训练一点帮助都没有。

所以定了四步清洗。第一步过滤非文本消息，图片、语音、表情包、撤回消息全部删掉。第二步多轮对话切分，用30分钟时间窗口+Embedding相似度判断，把一段长对话切成独立的问答对。第三步两层脱敏，先用正则表达式匹配手机号、地址，再用NER模型识别人名、公司名，准确率能做到98%。第四步用LLM多维度评分——完整性、销售技巧、产品知识、语言质量、转化潜力，只保留4分以上的。

1000多条原始数据，洗完只剩200段高质量数据。虽然数量少了，但质量提升明显。

→ 为什么切分用30分钟作为窗口？

这是业务经验值。跨越速运的客服对话，如果客户30分钟没回复，通常意味着话题已经结束了，下一个问题大概率是新话题。Embedding相似度是做二次校验——即使时间没超过30分钟，如果两句话语义完全不相关，也会切分。

→ 脱敏准确率98%怎么验证的？

人工抽检。从清洗后的数据里随机抽100条，让3个人独立标注有没有漏脱敏的地方。如果3个人都认为没问题，就算通过。98%是抽检结果——100条里有2条有轻微漏脱敏，比如地址只脱了一半。

→ LLM评分的Prompt怎么写的？

定义了五个维度，每个维度1-5分。Prompt里给了评分标准和示例——比如"完整性"要求回答必须包含客户问题的所有方面，漏了一个方面扣1分。用GPT-4做裁判，比人工评分快，成本也低。

Q2: 为什么用两阶段训练策略？直接上云端训练不行吗？⭐⭐▶

主要是为了省钱和验证方向。云端训练按小时收费，如果数据有问题或者超参数设错了，跑几个小时才发现，钱就白花了。所以我们先本地用QLoRA快速验证——用Qwen2.5-3B在RTX 4090上跑40分钟，如果效果还行，说明数据质量和训练方向没问题。

本地验证通过了，再上云端做生产级训练。云端用豆包1.5的底座，LoRA rank=32，训练时间大概2-3小时。云端资源更稳定，能跑更大的batch size，最终模型的精度也更高。

→ 本地和云端训练出来的模型差异大吗？

差异不大，因为训练数据和方法完全一样，只是底座模型和硬件不同。本地验证主要是看训练过程是否收敛、评测指标有没有提升。如果本地都没提升，云端大概率也不行。

→ 如果本地验证通过了，云端训练效果反而不好怎么办？

这种情况发生过一次。本地用Qwen3B验证效果挺好，云端用豆包1.5训练后效果反而一般。后来发现是豆包1.5的Base模型和Qwen3B的指令遵循风格不一样，同样的数据在两个模型上表现不同。解决方法是调整数据格式，让数据更贴合豆包1.5的风格。

Q3: QLoRA和LoRA有什么区别？为什么本地用QLoRA、云端用LoRA？⭐⭐⭐▶

LoRA的核心思想是冻结原模型的权重，只训练一个低秩的增量矩阵。这样参数少、训练快、不占显存。QLoRA是在LoRA的基础上加了4-bit量化——把模型的权重从FP16压缩到4-bit，显存占用能降到原来的1/4。

本地用QLoRA是因为显存不够。RTX 4090只有24G显存，跑7B模型FP16要14G，加上LoRA和优化器状态就超了。4-bit量化后模型只占4G左右，剩下的显存够跑训练。云端用LoRA是因为云端显卡（A100 80G）显存充裕，不用量化也能跑，而且不量化精度更高，最终效果更好。

→ 4-bit量化对最终效果有影响吗？

有一定影响，但在本地验证阶段可以接受。我们的经验是4-bit量化的LoRA比FP16的LoRA在评测指标上低1-2个百分点，但训练速度快了3倍。本地验证主要看训练方向对不对，精度差一点没关系。

→ 除了LoRA和QLoRA，还考虑过其他PEFT方法吗？

看过Adapter和Prefix Tuning，但LoRA的生态最成熟，LLaMA-Factory、Hugging Face PEFT都支持得很好。Adapter效果也不错，但推理时要额外加载Adapter层，延迟增加比较明显。Prefix Tuning对长文本效果好，但我们的对话数据不长，用LoRA就够了。

Q4: SFT和DPO有什么区别？为什么需要两阶段？⭐⭐⭐▶

SFT解决"从不会到会说"。模型一开始不知道客服应该怎么说话，SFT用高质量的客服对话做监督学习，让模型学会基本的对话风格和话术。但SFT只能让模型"会说"，不能保证"说得好"。

DPO解决"会说但说不好"。具体做法是让评估员对同一批问题的两个回答做偏好排序——哪个更好、哪个更差。DPO让模型学习"好的回答比差的回答更受偏好"。这样模型不仅能说，还能说得更好。

我们选DPO而不是RLHF，是因为DPO跳过了奖励模型训练，直接用偏好数据优化。数据量不大的时候（几百条），RLHF的奖励模型训练不稳定，DPO更可靠。

→ DPO的偏好数据是怎么标注的？

找业务专家做A/B对比。同一个问题，模型生成两个回答，专家选哪个更好。标注标准是：是否准确、是否完整、语气是否合适、有没有多余信息。一条数据大概需要30秒，200条数据一个人半天就能标完。

→ DPO和RLHF的本质区别是什么？

RLHF三阶段：SFT→训练奖励模型→PPO优化。DPO两阶段：SFT→直接优化。DPO把奖励模型的学习隐含在优化目标里，简化了流程。缺点是DPO对偏好数据的质量要求更高——如果标注有噪声，DPO会学得比较偏激。

→ 只做SFT不做DPO，效果差多少？

我们对比过，只做SFT的人工盲评分数大概3.5分（5分制），加DPO后能到4.2分。主要提升在"回复质量"和"客户满意度"两个维度。SFT让模型学会了说话，DPO让模型学会了说"对的话"。

Q5: 为什么说"微调管风格、RAG管知识"？这个分工是怎么形成的？⭐⭐⭐▶

这个分工是吃过亏之后才明确的。一开始我们把产品知识也放进微调数据里，比如价格表、优惠政策、网点信息。结果发现知识一更新就要重新训练模型，训练一次要好几个小时，而且经常漏掉某些知识点——比如某个新网点开了，模型可能学了也可能没学。

后来我们做了职责分离：微调只学"怎么说话"——沟通风格、话术策略、对物流术语的理解。RAG只提供"说了什么"——产品信息、价格、时效、网点地址。这样知识更新只需要改RAG知识库，几分钟就生效，不用重新训练模型。

→ 如果训练数据里混入了产品知识，会有什么问题？

模型会"死记硬背"。比如训练数据里有"从上海到北京的运费是50元"，模型就会记住这个具体数字。但如果价格调整了，模型还是会说50元，因为它不知道价格变了。RAG的好处是实时检索最新价格，不会记错。

→ RAG提供的知识和微调学来的风格会不会冲突？

理论上会。比如RAG检索结果说"您的快递预计明天到达"，微调学来的风格是"非常抱歉给您带来不便"，两者结合可能变成"非常抱歉给您带来不便，您的快递预计明天到达"——语气上有点生硬。我们在Prompt里加了融合指令——"请用客服风格自然表达以下信息"，让模型把RAG信息和风格统一起来。

Q6: 物流领域的Embedding为什么要单独微调？通用模型有什么问题？⭐⭐▶

我们一开始用的是通用Embedding模型，发现检索效果一般。比如客户问"我的货卡在分拨中心了"，通用模型对"分拨中心"、"干线运输"这些物流术语的理解不够深，检索出来的结果经常是通用的快递FAQ，而不是跨越速运的内部操作流程。

所以专门用物流领域的数据做了Embedding微调。构建正负样本对的时候，正样本是同一类物流问题的不同问法，比如"货没到"和"快递延误"；负样本是语义相近但业务完全不同的，比如"改地址"和"改收货人"——看起来都像"改信息"，但业务流程完全不同。微调之后RAG检索的准确率从72%提升到了89%。

→ 用什么框架做的Embedding微调？

用的Sentence-Transformers，比较方便。训练数据大概5000对正负样本，在一张RTX 4090上跑了大概2个小时。推理的时候直接替换了原来的Embedding模型，对上层完全透明。

→ 正负样本对是怎么构建的？人工标注吗？

一部分是人工标注的，找业务专家标注了大概1000对"同义"和"不同义"的query对。另一部分是用规则生成的——同一类意图下的query两两组合作为正样本，不同意图的随机配对作为负样本。人工标注的质量高但慢，规则生成的量大但有一些噪声，两者混合训练效果还不错。

Q7: 微调模型上线前你们怎么做评估的？为什么说三层评估缺一不可？⭐⭐▶

我们吃过亏的。第一次微调完模型，自动指标看着都挺好，Perplexity低了、BLEU分高了，上线之后客户满意度反而下降了。后来分析发现自动指标只能保证"语法通顺"，保证不了"说的对不对"。

所以后来定了三层评估。第一层是自动指标，主要是排雷用的——如果自动指标比基线还差，直接打回，不用浪费人工评测资源。第二层是人工盲评，找3个业务专家各评50个case，用Cohen's Kappa算一致性，要保证评分标准统一。第三层是线上A/B测试，小流量对比，看真实业务指标。三层都通过才全量上线。

→ Cohen's Kappa值是多少？

我们要求Kappa值大于0.6，也就是"基本一致"。第一次评测的时候只有0.45，说明三个评估员的标准不统一。后来我们细化了一个评分细则，比如"是否提到了预计到达时间"算一分，"是否主动提供了补救方案"算一分，标准统一之后Kappa提到了0.72。

→ A/B测试的流量比例和观察周期是多久？

一般是5%的流量跑一周。跨越速运的客服流量不是特别大，5%大概一天有几百个对话，一周下来统计显著性够用了。主要观察两个指标：客户问题解决率（有没有帮到客户）和对话轮数（轮数太多说明模型理解能力差）。

Q8: 物流客服的意图分类为什么要单独微调？通用分类模型有什么问题？⭐⭐▶

通用意图分类模型在物流场景下表现很差。我们梳理了跨越速运的客服来电，发现物流意图比通用的"查询/投诉/表扬"要细得多——光是查询类就分查轨迹、查时效、查费用、查网点；变更类分改地址、改收货人、改配送时间；异常类分延误、破损、丢件。

通用模型把这些都当成"查询"，后续的对话流程就走错了。比如客户说"我的货坏了"，通用模型分到"查询"，系统就开始查轨迹而不是走破损处理流程。所以我们用2000多条标注好的物流客服对话做了意图分类微调，准确率从通用模型的68%提升到了94%。

→ 你们定义了多少种意图？

目前是12种核心意图，分三大类：查询类（查轨迹、查时效、查费用、查网点）、变更类（改地址、改收货人、改时间）、异常类（延误、破损、丢件、投诉、理赔）。还有一些低频意图归到"其他"里，走LLM自由回复。

→ 意图分类模型和LLM对话模型是怎么配合的？

意图分类是"守门员"，在对话的最前面决定走哪条路。分类结果决定后续的状态机流程：查轨迹就走轨迹查询子流程，改地址就走地址变更子流程。LLM负责在确定的流程里生成自然的回复。这样分工明确——分类模型快且准，LLM灵活但不稳定，不能让LLM来决定走哪个流程。

Q9: 微调好的模型是怎么接入语音客服系统的？对延迟有没有影响？⭐⭐▶

接入方式其实挺直接的——就是把原来调用通用LLM的地方换成微调模型，整个链路还是语音→ASR→RAG→LLM→TTS。但有一个意外的好处：因为微调模型已经学会了客服的对话风格，System Prompt可以缩短很多。

原来通用模型需要很长的System Prompt来告诉它"你是跨越速运的客服，说话要礼貌，要提及预计到达时间"，大概800个token。微调之后模型已经内化这些风格了，System Prompt缩短到200个token。Prefix Caching的命中率更高了，TTFT反而又降了大概300ms。

→ 推理延迟和通用模型比怎么样？

延迟基本一样，因为模型底座还是同一个，只是加了LoRA Adapter。推理的时候权重合并或者动态加载，额外开销可以忽略。如果走动态加载，第一次请求会多几十毫秒的加载时间，后面就正常了。

→ 上线是灰度发布的吗？

是的，先切了10%的流量跑了一周。观察指标主要是客户满意度和问题解决率。微调模型的满意度比通用模型高了一点（4.1 vs 4.0），问题解决率也略高。但最明显的变化是客户反馈"这个客服更懂物流"了——因为微调模型会主动用物流术语，比如"分拨中心"、"干线运输"这些，客户感觉更专业。

Q10: 如果让你重新做一次微调项目，你会在哪些地方改进？⭐▶

说实话有几个地方确实可以做得更好。第一是数据量，我们当时只有200段高质量数据，其实是远远不够的。后来看了业界的实践，500段以上是基本的，1000段以上才能比较稳定。数据量小导致模型在某些长尾场景上表现不稳定。

第二是评估环节。我们当时只有3个评估员，而且都是技术人员，缺少一线客服的视角。下次应该引入客服主管参与盲评，他们更能判断"这样说客户会不会满意"。

第三是线上数据回流。我们现在的训练数据都是离线整理的，上线后的优质对话没有自动回流到训练集里。下次应该建一个闭环：客户满意度高的对话自动入库，定期重新训练。

→ 为什么当时只有200段数据？

主要是数据清洗的门槛太高了。原始聊天记录有1000多条，但过滤掉非文本消息、广告、闲聊之后只剩600多条。然后做隐私脱敏，有些涉及客户手机号、地址的对话要删掉或打码。再用LLM评分筛选，只保留4分以上的。几轮筛选下来就只剩200段了。下次做的话，应该一开始就扩大原始数据的采集范围，比如从2000条开始。

Q11: 全量微调和LoRA微调怎么选？什么场景该用哪种？⭐⭐▶

全量微调（Full Fine-tuning）是更新模型的所有参数，LoRA是只训练一个低秩的增量矩阵。全量微调效果好但资源消耗大——7B模型全量微调至少需要4张A100，训练时间也长。LoRA只需要单卡，训练时间缩短到几小时甚至几十分钟。

选型看三个因素。第一是资源——如果有足够的GPU集群，全量微调效果更好。如果只有单卡或者预算有限，LoRA是不二之选。第二是数据量——全量微调需要更多数据才能充分训练所有参数，少于1000条的话LoRA更稳妥，不容易过拟合。第三是任务类型——如果是要模型学到全新的知识或能力（比如学会一门新语言），全量微调上限更高；如果只是调整风格或输出格式，LoRA足够了。

我们当时的策略是：本地用QLoRA快速验证方向，确认数据质量和训练方案没问题后，上云端用LoRA做生产级训练。没有走全量微调，因为成本高且收益在客服场景下不明显。

→ LoRA的秩（rank）怎么选？

rank决定了低秩矩阵的表达能力。rank太小（比如8），表达能力不够，模型学不到足够的信息。rank太大（比如128），参数量大了但收益递减，反而可能过拟合。我们在本地用RTX4090试了32/64/128几个值，最终rank=64在效果和速度之间最平衡。

→ 全量微调和LoRA的模型合并后有什么区别？

全量微调直接得到一个新的完整模型，推理时没有任何额外开销。LoRA训练完后要把低秩矩阵合并到原模型权重里（或推理时动态加载），合并后推理延迟与原始模型基本一致。但如果走动态加载（多个LoRA Adapter切换），第一次请求会多几十毫秒的加载开销。

Q12: 微调过程中过拟合了怎么办？怎么判断过拟合？⭐⭐▶

过拟合的判断看训练集和验证集loss的差距。训练loss持续下降但验证loss不再下降甚至开始上升，就是过拟合的典型信号。另一个信号是评测集上的自动指标很好但人工评测发现问题——模型"背"出了训练数据里的内容但没有泛化能力。

我们的处理策略分四个方向。第一是数据增强——增加训练数据的多样性，同一个意图用不同的表述方式扩充，减少模型死记硬背的可能。第二是正则化——LoRA本身有低秩约束就是一种正则化，还可以通过增大LoRA的dropout比例（从0.1提到0.3）来缓解。第三是早停（Early Stopping）——监控验证集loss，连续3个epoch没有改善就停止训练，这是工业界最常用的手段。第四是减少rank或epoch数——rank越大模型容量越大越容易过拟合，数据量不足时适当减小rank或减少训练轮次。

我们在项目里踩过这个坑：第一批数据只有200段，跑了10个epoch，训练loss降到了0.1但验证集评分反而比训练中期低。后来把epoch数从10减到5，加了dropout，效果好多了。

→ LoRA的dropout和全量微调的dropout效果一样吗？

不太一样。LoRA的dropout是加在低秩矩阵上的，相当于对增量部分做随机丢弃，不是对原始模型的隐藏层做dropout。这样可以防止LoRA Adapter过拟合到训练数据中的噪声，但不会影响原始模型的表征能力。效果上比全量微调的dropout更温和——因为原始模型的能力没有被丢弃。

→ 验证集怎么构建的？和训练集的比例？

从清洗后的数据中随机抽20%作为验证集，80%做训练。验证集和训练集用同样的清洗流程，保证分布一致。还有一个trick是确保验证集里每个意图类型都有覆盖，防止验证集只覆盖了高频意图。

Q13: 模型微调后出现了灾难性遗忘（Catastrophic Forgetting）怎么办？⭐⭐⭐▶

灾难性遗忘是微调中最常见的副作用——模型学了新的对话风格后，可能在通用能力（比如数学推理、常识问答）上出现退化。LoRA因为只更新低秩矩阵、冻结原始权重，比全量微调的抗遗忘能力好很多，但也不是完全免疫。

我们的做法是三层防护。第一层是评测集覆盖——在评测集里保留一定比例的通用能力测试case（比如20%），微调前后对比通用能力的分数，如果下降超过5%就不允许上线。第二层是LoRA rank控制——rank不要选太大，我们发现rank=64在风格调整场景下既能学好新风格又不会覆盖掉原有能力。第三层是数据配比——在训练数据中混入一部分通用对话数据（大概10-20%），让模型在学习新风格的同时"不忘本"。这个做法叫Experience Replay，在Continual Learning里用得比较多。

最关键的还是评测。我们第一次微调上线前只测了客服场景的指标，觉得挺好，上线后客户反馈模型偶尔回答一些常识问题时变笨了。后来在评测集里加了一组"通用能力"子集来专门监测遗忘情况。

→ 数据配比怎么确定？通用数据和领域数据的比例？

我们试了1:9、2:8、3:7几组比例。1:9对保留通用能力帮助不大，3:7又稀释了领域微调的效果。最后选了2:8——即20%通用对话数据 + 80%物流客服数据，既能保住通用能力又不影响领域效果。

→ 这个方案和Multi-Task Learning有什么区别？

思路类似，都是通过多任务训练防止遗忘。但Multi-Task Learning通常是一开始就用多个任务一起训练，我们是在微调阶段混合数据，更接近Continual Learning中的Experience Replay。如果从一开始就知道模型要做多个任务，应该用Multi-Task Learning设计训练方案。

Q14: 多轮对话的微调和单轮对话的微调有什么区别？处理方式有什么不同？⭐⭐▶

区别很大。单轮对话是一问一答，每条数据独立。多轮对话需要把完整上下文拼进去——模型不仅要理解当前问题，还要知道之前的对话历史。

处理上的差异主要在数据格式上。单轮对话的格式就是prompt + response。多轮对话需要把历史对话拼接成多轮格式——例如用<|im_start|>user/assistant分隔符把每一轮标记清楚。我们切分多轮对话时用了两个约束：一是时间窗口30分钟内的话题归为一组，超过30分钟判断为新话题；二是用Embedding相似度做二次校验，即使时间没超但如果语义完全不相关也会拆分。

另一个区别是注意力掩码（Attention Mask）的设置。单轮对话所有token的注意力是完整的。多轮对话通常用Causal LM的方式，每个token只能看到它之前的token——这正是标准decoder-only模型的自回归方式，所以不用额外处理。但如果用的是Encoder-Decoder模型（比如T5），训练时会把整个多轮对话拼成输入，只在最后一个回复部分计算loss。

我们用的是Qwen2.5（decoder-only），所以直接把多轮对话拼成标准格式就行了，loss只计算assistant回复部分的token。

→ 多轮对话微调时，loss怎么计算？只算最后一轮还是每一轮都算？

我们只算assistant回复部分的token loss，user输入部分不贡献loss。这是行业标准做法——训练模型生成好的回复，不是训练模型理解输入。如果所有token都算loss，模型会学到"复读用户问题"而不是"回答用户问题"。

→ 长多轮对话的上下文长度怎么控制？

设置最大长度上限，超出的部分截断最早的历史。我们的模型支持8K上下文，但训练时用了4K max length——超过4K的对话截断最旧的历史轮次。测试下来4K能覆盖95%以上的客服对话场景。太长的话训练成本高且收益有限。

【八股文】Fine-tuning & PEFT 理论题 ⭐⭐⭐▶

Q1: Transformer的Self-Attention公式是什么？为什么需要Scaled Dot-Product？

公式 Attention(Q,K,V) = softmax(QK^T / √d_k) V。Q是Query矩阵，K是Key矩阵，V是Value矩阵，d_k是Key向量的维度。除以√d_k的原因是防止点积结果过大。当d_k很大时，QK^T的点积值会随维度增加而变大，导致softmax的梯度进入饱和区（极端值附近梯度接近0），影响训练稳定性。除以√d_k把方差拉回到1，保持梯度正常。

Q2: Layer Normalization和Batch Normalization有什么区别？LLM为什么用Layer Norm？

Batch Norm对每个特征维度在batch方向上做归一化，依赖batch size，训练和推理行为不一致。Layer Norm对每个样本的所有特征维度做归一化，不依赖batch size，训练和推理行为一致。LLM用Layer Norm的原因：一是文本序列长度可变，Batch Norm对变长序列处理麻烦；二是Layer Norm对每个token独立归一化，更适合序列模型；三是训练时batch size通常较小（显存限制），Batch Norm在小batch下统计不稳定。

Q3: 什么是PEFT？主流方法有哪些？怎么选？

PEFT（Parameter-Efficient Fine-Tuning）是在不更新全部模型参数的前提下微调大模型的方法族。主流方法分三类：Adapter类（在Transformer层之间插入小网络，只训练Adapter参数，推理时有额外延迟）、Prefix Tuning类（在输入前添加可训练的虚拟token，对长文本效果好但可解释性差）、LoRA类（用低秩矩阵近似增量更新，推理时可合并权重零额外开销）。目前工业界最流行的是LoRA，生态最成熟，HuggingFace PEFT和LLaMA-Factory都支持。

Q4: LoRA的rank和alpha参数的关系？alpha=128, rank=64意味着什么？

LoRA更新公式：h = W₀x + (α/r)·BA·x。B∈R^(d×r)，A∈R^(r×k)，BA的秩为r。α是缩放系数。alpha=128, rank=64意味着α/r = 128/64 = 2，即LoRA更新量放大2倍。推荐初始值alpha = rank，根据训练loss调整，如果loss下降太慢可适当增大alpha。

Q5: SFT、DPO、RLHF三者的区别和适用场景？

SFT用高质量数据做监督学习，让模型学会"正确"回答，适用于风格调整。但不能区分"好"和"更好"。RLHF三阶段：SFT→训练Reward Model→PPO优化，效果上限最高但训练不稳定、显存开销大。DPO跳过Reward Model，直接用偏好数据优化，实现简单但偏好数据质量要求高。选型：数据量小（几百条）选DPO，数据量大且资源充足选RLHF。SFT是前两者的前置步骤。

Q6: 什么是Perplexity？它和BLEU/ROUGE有什么区别？

Perplexity衡量模型对下一个token预测的不确定性，PPL = exp(-1/N·∑log P(w_i|context))。值越低说明模型预测越自信。PPL不需要参考答案，但PPL低不等于生成质量高——模型可能"自信地胡说"。BLEU/ROUGE需要参考答案，BLEU基于n-gram精确率适合翻译，ROUGE基于n-gram召回率适合摘要。坑：PPL很低但上线后客户满意度下降，因为PPL只能衡量"语法通顺"，衡量不了"说得对不对"。

Q7: 微调的核心超参数有哪些？经验值？

核心超参数：学习率（全量微调1e-5到5e-5，LoRA可大到1e-4到5e-4）、batch size（用gradient accumulation模拟大batch）、epoch（3-10轮，监控验证集loss早停）、warmup steps（前几步学习率从0线性增加到目标值）。LoRA特有参数：rank（8-128，取决于任务复杂度）、alpha（通常等于rank或2倍）、target modules（通常只加Attention的q_proj和v_proj）、LoRA dropout（数据量小时增大防过拟合）。LoRA训练后用merge_and_unload()合并权重再推理，延迟与原始模型完全一致。

P3: 基于 MCP 协议的 AI 多智能体共享集群（MCP 协议 / 多租户架构）

项目背景：跨越速运有多个AI业务（语音客服、智能导购、内容运营等），每个业务都需要LLM接入、知识检索、对话记忆、Prompt管理。如果没有统一基础设施，每个团队都要重复对接一遍。
核心痛点：① 各业务独立对接火山引擎API，重复建设严重 ② 没有统一鉴权/日志/配额管理 ③ Prompt散落在代码里，版本不可追溯 ④ 多业务数据隔离困难。
服务对象：语音客服、智能导购、内容运营、工单系统等多个业务线的AI Agent。
技术栈：MCP协议 / 火山引擎ARK / 阿里云Serverless（FC+SAE）/ Redis / PostgreSQL / REST-MCP网关 / YAML Schema / Streamable HTTP。
关键效果：多业务接入周期从8周缩短至2天，标准化原语暴露实现共享服务，多租户逻辑隔离+物理共享，弹性伸缩支撑峰值流量。
面试话术：做了P1和P2之后，发现多个业务线都在重复建设LLM网关、RAG检索、会话记忆这些基础能力。所以用MCP协议把它们抽成了四个共享Server：LLM网关管模型路由和限流，RAG检索管知识库，会话记忆管对话上下文，Prompt模板管提示词版本。流程是：业务Agent发请求→REST-MCP网关做鉴权和转换→路由到对应MCP Server→返回结果。坑主要有两个：一是MCP的Streamable HTTP和SSE标准在变，我们做了适配层屏蔽差异；二是多租户隔离，业务团队要求数据完全隔离，但完全隔离成本太高，最后做了逻辑隔离——RAG用Collection前缀，记忆用user_id+project_id，底层物理存储共享，既保证了隔离又控制了成本。

Q1: 在跨越速运的多个AI项目并行推进时，为什么选MCP协议而不是直接调REST API？⭐⭐⭐▶

这个问题我们内部争论了很久。一开始每个项目都是直接调REST API，语音客服调一套，智能导购调另一套，RAG检索又调第三套。结果就是每个项目都有自己的鉴权方式、错误码规范、日志格式，维护起来特别痛苦。新员工入职要配三四个API Key，排查问题要切三四个平台。

后来我们发现MCP协议其实就是把"怎么暴露服务"这件事标准化了。所有能力都包装成MCP Server，不管是RAG检索还是Prompt模板，对外都是统一的接口格式。Agent通过MCP协议自动发现有哪些Tool可以用，不用硬编码API地址。对我们这种多Agent、多项目并行的团队来说，MCP相当于在中间加了一层抽象，让共享服务真正能被共享。

→ MCP协议本身有性能开销吗？

有一定的序列化开销，但对我们来说几乎可以忽略。因为MCP底层还是走HTTP，和我们原来直接调REST的传输成本是一样的。多出来的是JSON Schema的解析和Tool发现的过程，这部分在启动时做一次就好了，运行时基本没有额外开销。

→ 如果只有一两个Agent，还有必要用MCP吗？

如果只有一个Agent调一两个API，确实没必要，直接硬编码最简单。但我们的场景是语音客服、智能导购、内容运营三个业务线共享同一套底层能力，而且后续还会接入更多业务。MCP的前期投入在第三个项目接入的时候就回本了——新业务只需要写Agent编排层，底层服务自动可用。

Q2: MCP和Function Calling是什么关系？它们会互相替代吗？⭐⭐⭐▶

它们是完全不同的两个层面的东西。Function Calling是LLM的"能力"——模型本身要支持FC，它才能决定什么时候调用工具。MCP是"协议"——规定了工具应该怎么暴露、怎么描述、怎么被调用。

打个比方，FC是顾客看菜单点菜的能力，MCP是餐厅怎么写菜单、怎么上菜的规范。一个LLM支持FC，但它不知道你的RAG检索服务在哪里、参数是什么；MCP协议就是告诉它"这里有个检索服务，参数是query和top_k"。

所以它们是互补关系，不是替代关系。LLM通过FC决定要做什么，MCP协议告诉它具体怎么做。

→ LLM能直接调API，为什么还要包一层MCP？

直接调API当然可以，但每个API的鉴权方式、参数格式、错误处理都不一样。MCP把这些差异都封装掉了——对LLM来说，所有工具都是一个统一的JSON Schema接口。而且MCP支持Tool Discovery，LLM能自动发现有哪些工具可用，不用在Prompt里硬编码。

→ MCP Server返回的结果是怎么给LLM的？

MCP返回的结果会格式化成JSON，然后通过Function Calling的结果字段回传给LLM。LLM拿到结果后继续生成回复。整个过程对业务代码是透明的——业务代码只负责定义Tool，不用管数据怎么流转。

Q3: MCP网关的四层中间件具体是怎么设计的？解决了什么问题？⭐⭐▶

网关是我们后来加的，一开始直接暴露MCP Server，很快就出问题了。一是不同项目的流量互相影响，语音客服的峰值把RAG检索打挂了，内容运营也跟着报错。二是出了故障定位困难，四个Server的日志格式都不一样，排查一个问题要切四台机器。

所以加了四层中间件：第一层是认证层，统一用API Key鉴权，每个项目发一个Key，过期自动轮换。第二层是日志层，所有请求统一打Trace ID，全链路可追踪。第三层是配额层，每个Key配Token配额，用完就限流，防止一个项目把资源吃光。第四层是路由层，根据请求类型把流量分发到不同的MCP Server，还可以做灰度发布。

→ 网关本身会不会成为单点故障？怎么保证高可用？

网关部署了两台机器做负载均衡，后面还可以水平扩展。但说实话目前还没到那个量级，两台足够用了。每个MCP Server也是独立部署的，一个挂了不影响其他的。网关层有健康检查，发现后端挂了会自动摘流量。

→ 配额用完之后是直接拒绝还是降级？

默认是直接拒绝，返回429。但关键业务比如语音客服，我们配了降级策略——配额用完之后走本地缓存的兜底回复，至少不会让客户听到"系统繁忙"。不过这个兜底回复的质量一般，只是保证可用性。

Q4: 跨越速运有三个业务线共用这套MCP集群，多租户隔离是怎么做的？⭐⭐⭐▶

多租户隔离是我们设计时重点考虑的问题。跨越速运内部有不同的业务团队——语音客服团队、智能导购团队、内容运营团队——他们共享同一套底层能力，但数据绝对不能串。

RAG检索层面，每个项目有独立的Collection，用project_id做前缀隔离。比如语音客服的Collection叫"voice_123"，导购的叫"guide_456"，检索时只能查自己项目的数据。会话记忆层面，短期对话记忆用session_id隔离，不同会话之间互不可见；长期用户画像用user_id做键，但每个画像字段都带project_id标签，一个用户在不同项目下的画像数据不会混在一起。网关层面，每个项目发独立的API Key，配额也是独立的，用完一个项目的配额不会影响其他项目。

→ project_id的粒度是什么？是项目级别还是团队级别？

目前是项目级别。一个业务团队可能有多个项目，比如客服团队就有语音客服和在线客服两个项目，它们的数据也是隔离的。project_id在创建项目时自动生成，所有资源都挂载在这个ID下面。

→ 同一个用户在语音客服和智能导购里的画像数据会不会串？

不会。画像数据在PG里存储时，主键是(user_id, project_id)的组合。即使同一个手机号在客服和导购都出现过，两边的画像数据也是完全隔离的。这也是为了合规考虑——客服的投诉记录和导购的购买偏好不应该被混在一起。

Q5: 你们设计了双层记忆架构，对话记忆和用户画像分别解决了什么问题？⭐⭐⭐▶

这个设计其实是从客服的实际痛点里长出来的。我们发现客服有两个完全不同的记忆需求：一是"刚才说了什么"，比如客户前一句问"我的货到哪了"，后一句说"那什么时候能到"，这个"那"指的是前面的货，如果忘了上下文对话就接不上。二是"这个客户是谁"，比如客户是跨越速运的月结大客户还是散户，之前的投诉记录是什么，这些背景信息对服务质量影响很大。

所以分了双层：短期对话记忆管"刚才说了什么"，按session_id隔离，存在Redis里，TTL设为30分钟，超过没新消息就自动清掉。长期用户画像管"这个客户是谁"，按user_id存储，存在PostgreSQL里，每次对话结束后用LLM提取关键信息，UPSERT更新到画像表里。两层互相独立但配合工作——对话记忆保证上下文连贯，用户画像提供个性化服务。

→ 用户画像的更新策略是什么？会不会越积越多？

有收敛策略。同一个key多次更新时，LLM会做一个合并判断——如果新值和旧值冲突，保留新值；如果是不同维度就追加。还有一个定期清理策略，超过90天没有更新的画像字段会被标记为过期，但不会删除，避免冷启动时完全没有画像数据。

→ LLM提取画像信息的准确率怎么样？

大概85%左右。有些隐式信息提取不太准，比如客户说"你们上次就搞错了"，LLM不一定能正确归类为"历史投诉记录"。为了提高准确率，我们加了一层规则校验——提取出来的信息必须符合预定义的Schema，类型不对的直接丢弃。

Q6: Agent的七步编排流水线具体是怎么工作的？⭐⭐▶

这七步是我们从实际业务中沉淀出来的标准流程。客户发来一句话，Agent先召回历史对话（Redis查session_id），然后读用户画像（PG查user_id），接着检索知识库（RAG查向量库），然后渲染Prompt（把历史、画像、知识片段拼成完整上下文），再调LLM推理，推理完保存本次对话到记忆，最后提取事实更新画像。

这个顺序不能乱。比如必须先读画像再检索知识，因为画像里可能有客户的VIP等级，VIP客户和普通客户的知识库检索范围不一样——VIP客户能看到内部处理进度，普通客户只能看到公开信息。

→ 这七步是串行执行的吗？有没有可以并行的？

大部分是串行的，因为后面依赖前面的结果。但"读画像"和"检索知识"这两步其实可以并行——画像和知识库没有依赖关系。我们在实现时把这两步并行化了，能省掉大概100-200ms的延迟。

→ 如果中间某一步失败了怎么办？

看哪一步。如果是RAG检索失败，就降级为不带知识库的通用回复，至少对话还能继续。如果是LLM推理失败，会重试一次，重试还失败就返回"系统繁忙"的兜底话术。如果是保存记忆失败，不影响本次回复，但会打告警，因为画像更新会丢失。

Q7: 为什么要用MCP的Prompt原语来管理提示词，而不是直接硬编码在代码里？⭐⭐▶

硬编码的痛苦我们经历过。一开始Prompt就是Python字符串，改一个字节就要重新部署，发布一次要15分钟。而且不同环境的Prompt经常不一致——开发环境改了一个词，生产环境忘了同步，排查问题的时候发现两边表现不一样，特别痛苦。

后来我们用了MCP的Prompt原语，本质上是把Prompt当成一种"资源"来管理，通过YAML Schema定义，存在Prompt Server里。业务代码只引用一个名字，比如"customer_service_greeting"，真正的Prompt内容在服务端渲染。运营同学想改欢迎语，直接在管理后台编辑，保存后即时生效，不用发版。

→ Prompt版本管理怎么做？

每次修改都会自动保存一个版本，可以回滚到任意历史版本。还有一个灰度发布功能——先给10%的流量用新版本，观察指标没问题再全量。这个功能救过我们好几次，有一次新版Prompt在测试环境看着没问题，上线后才发现有个边界case处理得不好，灰度期间及时发现回滚了。

→ 业务代码和Prompt是怎么解耦的？

业务代码完全不碰Prompt内容，只传变量。比如客服场景代码里就一行：render_prompt("customer_service_greeting", customer_name="张三")。真正的Prompt模板在服务端，运营同学可以随便改，只要不删掉customer_name这个变量占位符就行。

Q8: 为什么选择阿里云Serverless部署MCP集群？有什么优势和坑？⭐⭐▶

一开始我们是用独立Docker部署的，维护起来很麻烦。MCP集群有4个Server加上网关，每个都要自己配机器、配负载均衡、配日志采集。出问题了还要SSH上去看日志，半夜报警特别痛苦。

后来迁到阿里云的函数计算FC和SAE。函数计算适合那些请求处理完就结束的无状态服务，比如RAG检索和Prompt渲染；SAE适合需要常驻的服务，比如会话记忆和LLM网关。自动弹性伸缩挺香的——流量大了自动扩容，流量小了自动缩容，不用半夜起来手动加机器。

→ Serverless冷启动会不会影响延迟？

会的，函数计算的冷启动大概要1-2秒。我们做了两个优化：一是给核心服务（RAG检索）配置了最低保留实例，保证始终有 warmed-up 的实例。二是把一些轻量调用合并到常驻服务里，减少冷启动触发。

→ 服务之间是怎么发现的？

用阿里云的服务注册中心，每个MCP Server启动时自动注册，网关从注册中心拉取可用实例列表。如果某个实例挂了，健康检查会把它摘掉，网关自动把流量切到健康的实例上。

Q9: MCP协议从SSE升级到Streamable HTTP，这个改动带来什么变化？⭐⭐▶

这是一个比较大的协议升级。SSE是单向的，服务器只能推数据给客户端，客户端如果要发新请求得再开一个连接。Streamable HTTP是双向的，一个连接里既能推又能拉，而且支持标准HTTP语义，代理、防火墙都更容易兼容。

对我们实际的影响主要是两点：一是连接数减少了，原来一个Agent可能要维持四五个SSE连接，现在一个就够了。二是错误处理更标准了，SSE的错误码不规范，Streamable HTTP可以直接用HTTP状态码，排查问题更容易。

→ 升级过程中有没有兼容性问题？

有的。我们升级的时候新老版本的Agent并行跑了一段时间，网关层做了协议适配——老版本Agent走SSE，新版本走Streamable HTTP，网关负责统一转发的后端MCP Server。等所有Agent都升级完了才把SSE的适配代码下掉。

Q10: 新业务团队想接入这套MCP集群，大概要多久？需要做什么？⭐▶

现在接入很快，从原来的2周压缩到了2天。流程是：先在管理后台申请一个API Key，配置配额和权限；然后在自己的Agent代码里引入MCP客户端SDK，写Agent编排层——也就是定义遇到什么情况该调用哪个Tool；最后跑一遍集成测试，通过就上线了。

底层的服务完全不用改，RAG检索、会话记忆、Prompt模板都是现成的，直接复用。新业务团队只需要关注自己的业务逻辑，不用关心底层能力怎么实现的。

→ 如果新业务需要的能力在现有MCP Server里没有怎么办？

有两种处理方式。如果是通用能力，比如新的数据源接入，我们会评估是否值得新增一个MCP Server，让所有人共享。如果是业务专属能力，新业务团队可以自己开发一个MCP Server，接进来就好了。我们有一套MCP Server的开发模板，从开发到接入大概一周。

Q1: 跨境物流涉及纸质面单、Excel、PDF、邮件附件等多源单据，LangGraph怎么统一处理这些格式差异？⭐⭐▶

跨越速运的跨境单证来源很杂——客户可能拍一张纸质面单的照片，也可能是Excel报关明细、PDF发票，甚至是邮件里的附件。这四种格式的数据结构完全不一样：纸质面单需要OCR+版面分析；Excel需要按列名映射到标准字段；PDF需要区分文本区和表格区；邮件附件还要先解压再识别格式。

我们在LangGraph的第一步"单据解析"节点做了格式识别和统一转换。上传文件后，先判断MIME类型，然后走对应的解析器：图片走OCR（印刷体准确率97%，手写体85%），提取运单号、收发货人、货物名称、重量、件数等关键字段；Excel按预设的列名映射表转成标准Schema，支持多种模板；PDF用版面分析区分文本和表格，表格转结构化数据；邮件先解析正文和附件，附件递归走上面的流程。四种格式最终都输出成同一个Pydantic DocumentSchema，后面的节点不用关心原始格式是什么。

→ 解析失败的单据怎么办？

进人工兜底队列。解析器会返回置信度，低于阈值的单据不往后走自动流程，直接分配给关务专员处理，并标注"解析失败"原因，后续用来优化解析器。

→ 不同客户的Excel模板不一样怎么办？

我们维护了列名映射表，支持别名匹配。比如"货物名称"可以匹配"品名""商品名""Item Description"等。新模板提交后，运营同事配置映射关系，不用改代码。

→ PDF版面分析和Excel表格识别有没有调研过业界开源方案？

调研过。小红书开源的 dots.ocr（1.7B）和 FireRed-OCR（2B）在文档解析上表现很亮眼——dots.ocr 在 OmniDocBench 上表格解析 TEDS 88.6%，支持端到端 PDF 解析和 Excel 生成；FireRed-OCR 用格式约束强化学习解决结构幻觉，在 OmniDocBench v1.5 上排名第一。我们内部也跑过评测，对复杂版面的 PDF 发票和嵌套表格的 Excel 报关单，效果确实比传统 PaddleOCR + 版面分析的 Pipeline 好一截。但考虑到跨境单证涉及客户商业敏感信息，数据不能出内网，而 dots.ocr 和 FireRed-OCR 需要 GPU 部署，我们当时的 GPU 资源主要分配给 LLM 推理，所以没有直接上线，而是借鉴了它们的端到端 VLM 架构思路——把版面检测、文本识别、表格解析放到一个模型里统一做，减少了传统 Pipeline 的误差累积。后续如果 GPU 资源扩充，会优先试点这两个模型。

Q2: HS编码自动归类是怎么做的？准确率多少？⭐⭐▶

HS编码（海关编码）是跨境物流最核心的字段，直接决定关税税率和监管条件。但HS编码有6位国际通用码、8-10位中国细分码，品类描述和编码的对应关系很复杂，人工归类一份单据要5-10分钟，还容易出错。

我们的"合规审查"节点用"LLM语义理解 + 规则引擎校验"的混合方案做HS编码自动归类。第一步，LLM根据货物描述（比如"无线蓝牙耳机"）输出候选HS编码和置信度，同时给出归类依据（功能、材质、用途）。第二步，Drools规则引擎根据候选编码查询监管条件（是否需要商检、是否需要许可证、关税税率），判断这个编码是否合理。比如货物描述是"锂电池"，LLM给了8507（蓄电池），规则引擎发现这批货是手机配件，应该归8518（耳机）而不是8507，就会打回重新归类或标记人工复核。

当前准确率大概在92%左右，规则引擎二次校验后能纠偏3-4%，最终有效归类准确率在95%以上。对于高价值货物（申报价值超5000美元），无论LLM置信度多高，都会强制走人工复核。

→ HS编码归类错了有什么后果？

轻则退单重报，延误3-5天；重则海关扣货、罚款，甚至影响企业信用等级。所以高价值货物必须人工复核。

→ 新商品品类怎么扩展？

LLM的泛化能力能覆盖大部分新商品，因为归类依据（功能、材质、用途）是通用的。如果遇到完全没见过的新品类，先走人工归类，结果沉淀到训练数据里，下次就能自动覆盖。

Q3: 多源比对环节是怎么做的？怎么发现不同单证之间的不一致？⭐⭐▶

跨境物流一票货物涉及多个单证，这些单证上的信息必须一致。比如商业发票上写的货物重量是50kg，但装箱单上写的可能是55kg；原产地证上的发货人和提单上的发货人不一致，海关就会退单。

"多源比对"节点把单据解析出来的字段，在多个单证之间做交叉验证。比对分三个维度：基础信息（运单号、收发货人、地址）必须在所有单证中完全一致；货物信息（品名、重量、件数）允许小差异——重量允许±5%误差（不同称重设备有浮动），件数必须完全一致；单证间逻辑关系——比如原产地证的货物描述必须和商业发票一致，MSDS上的货物名称必须和报关单一致。

比对结果生成差异报告，标红不一致项，后面的"合规审查"节点会根据差异类型决定是否需要补单或人工复核。

→ 三个单证都冲突怎么办？

按可信度排序——系统电子底单优先级最高（发货时录入的原始数据）；PDF发票次之；纸质面单最低（可能是最新修改但不一定准）。如果三者都冲突，标记为"严重信息不一致"，直接进人工复核。

→ 比对阈值是怎么定的？

基础信息硬匹配，差一个字都不行。重量±5%，件数完全一致。这些阈值是和关务团队一起定的，考虑了实际业务中的合理浮动。

Q4: 你们涉及中国海关、美国FDA、欧盟CE等多国合规规则，LangGraph里是怎么做规则审查的？⭐⭐▶

跨境物流最大的合规风险就是各国规则不一样。中国海关对申报价值和HS编码有严格限制，美国FDA对食品/药品/化妆品有准入要求，欧盟CE对电子/机械产品有认证要求，还有锂电池的UN38.3、危包证等特殊要求。人工审查的时候经常漏掉某一条，导致货物被扣或退单。

"合规审查"节点是一个混合架构：Drools规则引擎管"硬规则"，LLM管"软规则"。硬规则是明确的法规条文——比如"申报价值超过1000美元必须提供商业发票""电子产品到欧盟必须有CE认证""锂电池空运必须提供UN38.3和MSDS"，这些写成drl规则文件，确定性的if/else判断，不会错。每个国家一套规则文件，按目的国动态加载。

软规则是语义理解类的——比如"这个货物描述是否涉及敏感词（如军用、警用）""这个品类是否需要额外的检验检疫证书""货物描述和HS编码是否语义匹配"，这些走LLM判断，因为规则条文很难穷举所有情况。LLM和规则引擎的结果合并，生成合规检查报告，标明"通过""警告""不通过"三类。不通过的直接阻断，警告的进入人工复核。

→ 规则引擎用的是什么？

Drools。规则写成drl文件，热更新不用重启服务。

→ LLM判断规则会不会幻觉？

会，所以LLM只负责打标签和提示风险，最终决策权在规则引擎。LLM说"这个可能涉及FDA"，规则引擎再去查FDA的具体条款确认。不给LLM直接放行或拦截的权限。

→ 规则更新频率高吗？怎么维护？

海关HS编码和税率相对稳定，一季度更新一次。FDA、CE的政策变动比较频繁，我们订阅了官方RSS，有更新时自动提醒，法务同事审核后更新规则文件。当前200多条规则，维护成本每月约2人天。

Q5: 缺失项识别和自动补单是怎么实现的？⭐⭐▶

合规审查完成后，系统会知道这票货"缺什么"——可能是缺原产地证，可能是MSDS版本过期，可能是CE认证证书不在有效期内。传统方式是关务专员人工联系客户补单，平均要1-2天。

我们的"缺失项识别"节点根据合规审查报告，自动生成缺失单证清单。然后分两条路："自动补单"和"人工复核"。能自动补的单据，系统直接调用海关单一窗口API或内部ERP接口生成——比如原产地证信息可以从发货人档案里自动填充，商业发票可以根据订单数据自动生成。不能自动补的（比如需要客户盖章的证书、需要第三方检测机构出具的报告），生成补单通知推送给客户，同时标注预计处理时间。

LangGraph里用条件分支实现：缺失项识别后，判断每个缺失项是否"可自动生成"，能的走自动补单分支，不能的走人工复核分支。自动补单完成后再次进入合规审查，形成闭环。

→ 自动补单的准确率怎么保证？

自动生成的单据走同样的合规审查流程，不降低标准。如果自动补单后审查不通过，回滚到人工复核。

→ 客户不配合补单怎么办？

飞书/短信/邮件三通道提醒，24小时未响应自动升级给销售或客服跟进。有专门的SLA监控。

Q6: 自动补单和人工复核的边界怎么划分？⭐⭐▶

自动补单和人工复核的边界是"确定性和风险"的权衡。能自动补的必须满足三个条件：第一，数据来源确定——比如可以从系统档案或订单数据直接提取，不需要客户提供新材料；第二，规则明确——生成逻辑是固定的，不需要人工判断；第三，风险可控——即使错了也能快速回滚，不会造成海关罚款或货物扣押。

具体场景上：商业发票、装箱单、简单的原产地申报可以自动补；需要第三方机构出具的证书（UN38.3、MSDS、CE认证）、需要客户盖章或签字的单据、高价值货物的附加文件，必须走人工复核。另外，申报价值超过5000美元的货物，即使所有单证都齐了，也强制走人工复核。

这个边界是和关务团队、法务一起定的，每季度根据实际运行数据调整。当前自动补单率大概在60%左右，也就是说60%的缺失项不需要人工干预。

→ 自动补单率60%是怎么统计的？

按缺失项数量统计。比如一票货缺3项，其中2项自动补了，1项人工复核，这票的自动补单率就是66.7%。月度平均下来在60%左右。

→ 自动补单出错过吗？

出过。早期有一次自动生成的商业发票币种写错了，导致海关计税错误。后来加了二次审查——自动补单后的单据必须再走一遍合规审查，且高价值货物强制人工复核。

Q7: Human-in-the-Loop在通关前复核是怎么实现的？挂起期间数据会不会丢？⭐⭐▶

合规审查中有三个环节必须人工介入：高价值货物复核（申报价值超5000美元）、合规审查"警告"类判定、自动补单后仍不通过的case。这三个环节都用了LangGraph的interrupt/resume机制。

当流程走到需要人工介入的节点时，调用interrupt()把当前状态持久化到PostgreSQL Checkpointer里。状态包括：当前走到哪个节点、所有单证的解析结果、多源比对报告、合规审查结果、缺失项清单、自动补单记录。然后发飞书通知给关务专员，审批人点开链接能看到完整的case档案，就像看一份完整的通关资料包。

审批人点通过或驳回后，系统调用resume()恢复流程。即使挂起期间服务重启了，从PG里读出快照就能精确恢复，不会让客户重新提交。Checkpointer每经过一个节点就自动保存一次，相当于给整个流程做了增量备份。

→ 状态快照存在哪里？结构多大？

PostgreSQL的langgraph_checkpoints表。一个完整的状态快照大概几百KB到几MB不等，主要是单证图片的base64比较大。我们在Checkpoint里只存图片的引用ID，实际图片存在对象存储里。

→ 支持回滚到上一步吗？

支持。LangGraph的Checkpointer保存了历史版本，可以回滚到任意一个checkpoint重新执行。调试的时候特别有用——比如发现合规审查规则有bug，可以回滚到审查节点重新跑，不用从头解析单据。

Q8: 复盘节点在整个流程里起什么作用？怎么沉淀合规知识？⭐⭐▶

复盘是七步闭环的最后一步，不是简单的"结束了"。通关放行后，系统自动生成一份复盘报告：单证齐备率分析（哪些单证经常缺失）、合规审查通过率（哪些规则经常触发警告）、HS编码归类准确率（哪些品类容易错）、处理时长分析（哪个环节耗时最长）。这份报告同时发给关务团队、运营团队和质控团队。

更重要的是知识沉淀。每次复盘的结果会更新到三个地方：一是Drools规则引擎——如果发现某类货物的合规规则有漏洞，就补充新规则。二是HS编码训练数据——把归类错误的case加入微调数据集，优化LLM的归类能力。三是单证模板库——如果发现某类客户经常缺同一种单证，就预设补单模板，下次自动推荐。

→ 复盘报告是自动生成的还是人工写的？

框架是自动生成的，LLM根据流程数据填充各个字段。但关键结论需要关务主管确认——比如根因分析是否正确、规则调整建议是否合理。主管每天花大概30分钟审报复盘报告。

→ 复盘数据怎么反哺前面的节点？

每周做一次数据回流。比如发现某类单据解析经常出错，就优化解析器的Prompt或规则。发现某条合规规则的误报率高，就调整规则阈值。这样整个系统是自我进化的。

Q9: 你们用了Pydantic Schema和JSON Mode，这在单证中台里解决了什么问题？⭐⭐▶

单证中台的链路很长，从单据解析到通关放行有十几个节点，每个节点都要传递数据。如果数据格式不统一，前面节点输出的字段后面节点不认识，整个流程就崩了。

我们用Pydantic Schema定义了每个节点的输入输出结构。比如"单据解析"节点输出的是DocumentSchema，包含运单号、收发货人、货物信息、单证类型等字段，每个字段都有类型、约束和默认值。后面的"多源比对"节点接收的也是DocumentSchema，保证数据结构一致。"合规审查"节点输出ComplianceReportSchema，包含HS编码、监管条件、合规状态、缺失项清单等字段。

JSON Mode保证LLM的输出一定是合法的JSON，不会输出乱七八糟的自由文本。我们在Prompt里嵌入Schema定义，LLM按Schema填充字段。如果LLM输出的JSON缺了必填字段或类型不对，Pydantic会自动校验并报错，不会把脏数据传到下一个节点。

→ Schema变更怎么办？

用Git版本管理。Schema变更要走Code Review，确保上下游节点都兼容。LangGraph的State是Pydantic BaseModel，字段变更会触发类型检查，不兼容的变更在开发阶段就能发现。

→ JSON Mode的输出质量比自由文本差吗？

在结构化任务上反而更好。因为JSON Mode限制了输出格式，模型不用纠结怎么组织语言，只需要填字段。自由文本适合对话场景，结构化输出适合流水线场景。

Q10: 单证中台和各个业务系统（ERP/WMS/关务系统/海关单一窗口）是怎么集成的？⭐⭐▶

单证中台不是孤立存在的，它需要对接多个上下游系统。上游对接ERP和WMS获取订单数据、库存数据、发货人档案；下游对接关务系统和海关单一窗口API完成报关报检。

集成方式分两种：实时调用和消息队列。单据解析和多源比对需要实时查ERP的订单数据，走HTTP API；通关放行后的数据回传、复盘报告的分发，走消息队列（RocketMQ），解耦且支持重试。海关单一窗口API是外部接口，有调用频率限制，我们做了令牌桶限流和降级——如果单一窗口挂了，先缓存报关请求，等恢复后批量重传。

LangGraph的"工具节点"封装了所有外部调用，每个工具都有超时、重试、熔断机制。比如查询ERP订单信息超时3秒就重试，重试3次还不行就标记"系统异常"进人工队列。

→ 外部系统挂了怎么办？

熔断+降级。比如海关单一窗口API挂了，报关请求先存在本地队列，等恢复后重传。如果ERP挂了，多源比对缺少系统数据，标记为"数据不完整"进人工复核，不会强行自动处理。

→ 数据一致性怎么保证？

关键操作（通关放行、自动补单）走分布式事务或最终一致性。通关放行前先写本地状态，再调单一窗口API，成功后更新状态。如果API调用失败，状态回滚，人工介入。

未来演进：GraphRAG 增强合规审查（Phase 2 规划）

当前 Drools + LLM 能覆盖 80% 的硬规则和软规则，但多国合规规则之间的**链式关联推理**是短板。比如"锂电池→德国→需要 UN38.3→UN38.3 要求 MSDS 报告→MSDS 必须由指定机构出具"，规则引擎需要写死每一层路径，维护成本高。

规划中的 GraphRAG 层：把**货物类型 / 目的国 / 法规 / 认证要求 / 检测机构**构建成 Neo4j 知识图谱，LLM 把自然语言查询转成 Cypher 查询做链式推理。GraphRAG 负责"发现隐藏关联"，Drools 负责"最终决策执行"，两者互补。

当前架构：货物类型 + 目的国 → Drools规则引擎 → 合规报告
Phase 2：货物类型 + 目的国 → Neo4j知识图谱 → LLM生成Cypher → 链式规则推理 → Drools决策执行 → 合规报告
Q11: 为什么不在单证中台里直接用知识图谱，而是等 Phase 2？⭐⭐▶

知识图谱的构建成本很高，需要领域专家（法务、海关、物流专家）一起梳理实体关系和图谱 Schema。当前 Drools + LLM 已经能覆盖 80% 的合规审查场景，上线价值优先。

GraphRAG 的真正价值在**链式推理**——当规则关联复杂到 3 层以上时（货物→认证→文件→检测机构），图谱的维护成本才会被节省下来的人工审核成本覆盖。我们算了笔账：当前规则 200 多条，人工维护 Drools 文件每月约 2 人天；如果上图谱，前期需要投入 1-2 个月构建 Schema 和实体，ROI 在当前规模下不划算。

→ 什么时候会上 GraphRAG？

当规则数量超过 500 条，或者业务扩展到 10 个以上国家时，链式推理的收益会超过构建成本。目前作为技术储备在跟进。

Q12: GraphRAG 和 Drools 在合规审查里是怎么分工的？⭐⭐▶

GraphRAG 管**推理发现**，Drools 管**决策执行**。比如关务专员问"这批锂电池去德国需要什么文件"，GraphRAG 在知识图谱里做链式推理，发现"锂电池→德国→需要 UN38.3 + MSDS + 危包证→UN38.3 必须由民航局认可的检测机构出具"，把这个推理路径和需要的文件清单返回。

Drools 拿到这个结果后，做最终的确定性判断——比如"UN38.3 证书是否在有效期内""MSDS 上的货物名称是否和报关单一致""检测机构是否在认可名单里"。这些硬规则不适合放在图谱里，因为它们是条件判断而不是关系推理。

→ GraphRAG 的查询延迟大概多少？

Neo4j 的 Cypher 查询在 10 万节点规模下大概 50-100ms，加上 LLM 生成 Cypher 的 1-2 秒，整体延迟 2-3 秒，在合规审查这种异步场景下可接受。

📋 跨境物流合规知识概念速查

HS编码（海关编码）： Harmonized System Code，6位国际通用码 + 8-10位中国细分码。决定关税税率、监管条件（是否需要商检/许可证）。归类依据：功能、材质、用途。

原产地规则： 判定货物"国籍"的规则。普惠制（GSP）——发达国家对发展中国家给予的关税优惠；一般原产地证（CO）——证明货物原产国；FTA优惠原产地证——区域贸易协定下的零关税或低关税凭证（如RCEP、中国-东盟自贸协定）。

准入认证： 各国对进口货物的强制性要求。美国FDA——食品/药品/化妆品/医疗器械；欧盟CE——电子/机械/玩具/建材；锂电池UN38.3——联合国危险品运输测试标准；MSDS——化学品安全技术说明书；危包证——危险货物包装性能鉴定。

核心单证类型（每票跨境货物5-8份）： 商业发票（Commercial Invoice）——交易价格和货物描述；装箱单（Packing List）——重量、件数、包装方式；提单/运单（B/L 或 Waybill）——运输合同和货权凭证；原产地证（CO/FTA）——关税优惠依据；检验检疫证书——动植物/食品/化妆品必须；MSDS/UN38.3——危险品必须。

海关单一窗口： 中国国际贸易"单一窗口"平台，报关、报检、缴税、放行一站式线上办理。企业端通过API对接，实现报关数据自动申报。

Q13: 你们规划中的知识图谱具体会怎么构建？实体和关系有哪些？⭐⭐▶

规划中的知识图谱核心是把"货物-法规-认证-文件-机构"之间的关联结构化。实体大概有5类：货物类型（锂电池、化妆品、电子产品）、目的国（美国、欧盟、德国）、法规（FDA、CE、UN38.3）、认证要求（MSDS、危包证、原产地证）、检测机构（民航局认可实验室、欧盟NB机构）。

关系主要是"需要"和"由...出具"两类。比如"锂电池→需要→UN38.3"、"UN38.3→由→民航局认可实验室出具"。还会加上条件属性——比如"UN38.3→有效期→1年"、"CE→适用范围→欧盟27国"。

构建方式上，前期用LLM从法规文本里抽取实体关系，法务和关务专家做人工校验。准确率目标85%以上才入库。Schema设计参考了行业通用的贸易合规本体。

→ 为什么选择Neo4j而不是其他图数据库？

两个原因。一是Cypher查询语法对LLM友好，LLM生成Cypher的准确率比生成SQL或Gremlin高。二是Neo4j的社区版够用，10万节点以内免费，部署成本低。我们测过Amazon Neptune和TigerGraph，功能更强但贵，当前规模下Neo4j性价比最好。

→ 知识图谱和传统关系型数据库有什么区别？

关系型数据库适合"已知查询"——比如"查这票货的HS编码"。知识图谱适合"未知关联"——比如"这个货物去德国需要什么文件"，需要遍历3-4层关系才能回答。关系型数据库要做这种查询需要写很多JOIN，维护成本高；图谱一行Cypher就能搞定。

Q14: GraphRAG和传统的向量RAG有什么区别？为什么合规审查更适合GraphRAG？⭐⭐▶

向量RAG是把文档切成chunk，转成向量存进向量数据库，查询时做相似度匹配。它擅长"找相关内容"——比如用户问"锂电池运输规定"，能召回所有提到锂电池的法规条文。但向量RAG不擅长"找关联关系"——比如"锂电池→德国→需要UN38.3→UN38.3要求MSDS"，这种跨文档的链式推理是短板。

GraphRAG的优势在关系推理。知识图谱把实体和关系显式建模，查询时是图遍历而不是相似度匹配。比如问"这批货去德国需要什么文件"，GraphRAG在图谱里从"货物类型"节点出发，沿着"目的国→法规→认证要求→所需文件"的路径遍历，把完整的推理链条返回。

合规审查的核心就是规则关联——货物类型和目的国决定了适用哪些法规，法规又决定了需要哪些认证，认证又决定了需要哪些文件。这种多层关联天然适合图谱。

→ 向量RAG和GraphRAG能不能一起用？

能，而且应该一起用。我们的规划是"向量RAG管文档召回，GraphRAG管规则推理"。比如用户上传一份MSDS，先用向量RAG判断这份MSDS的内容是否和报关单一致（语义比对）；再用GraphRAG判断"这个货物是否必须要有MSDS"（关系推理）。两者互补。

→ GraphRAG的构建成本高在哪里？

主要是Schema设计和实体抽取。Schema需要领域专家一起定——哪些实体、哪些关系、属性怎么设计。抽取需要高质量的标注数据，LLM自动抽取准确率大概70-80%，要达到可用水平（85%+）需要人工校验。前期投入1-2个月，之后每月维护成本约3-5人天。

Q15: 如果面试官质疑"你们P4项目其实就是个异常处理，不是什么合规中台"，你怎么回应？⭐⭐▶

这个质疑的核心是"异常处理"和"合规中台"的边界问题。我的回应分三层。

第一层，业务目标不一样。异常处理关注的是"出了问题怎么解决"——货丢了、延误了、破损了，核心是定责和赔付。合规中台关注的是"怎么让货顺利通关"——单证齐不齐、HS编码对不对、准入认证有没有，核心是预防退单和海关扣货。

第二层，流程设计不一样。异常处理是后置的——货已经出问题了才介入。合规中台是前置的——货还没发运或刚发运时就开始审查单证，发现问题提前补单，避免到海关才退单。我们的七步流程里"单据解析→多源比对→合规审查→缺失项识别→自动补单"都是前置动作，只有"通关放行→复盘"是结果。

第三层，技术架构不一样。异常处理更多是工作流编排（谁审批、谁赔付、通知谁）。合规中台的核心是规则引擎+知识库——Drools管硬规则、LLM管软规则、RAG管法规检索，未来还要上图谱做链式推理。两者的技术复杂度不在一个层面。

→ 如果面试官追问"那你简历上为什么写异常处理"？

（坦诚回应）早期项目立项时的定位确实是异常处理，因为业务团队最先感知到的是"跨境单证经常出问题导致货物被扣"。但随着项目深入，我们发现根因不是"处理异常"，而是"预防异常"——单证不齐、编码错误、认证缺失才是源头。所以项目逐步演进为合规中台，从后置处理转向前置审查。简历上的描述如果还是早期版本，确实需要更新。

P5: Agent Harness — 软件开发全生命周期工程框架与进化引擎

项目背景：大模型辅助编程（Vibe Coding）中极易陷入零散对话式无序探索、缺乏架构纪律与质量失控等痛点。团队需要一套能自我进化的标准化流程来管理产品开发全生命周期——从模糊想法到可运行、可发布的产品。
核心痛点：① 产品开发无标准流程，每个项目各自为政 ② 需求模糊不清，开发到一半才发现理解偏差 ③ 代码质量不可控，缺乏自动防线 ④ 团队经验无法沉淀，同样的问题反复踩坑 ⑤ AI辅助编码没有纪律约束，批量产出低质量代码。
服务对象：产品经理、全栈工程师、算法工程师。
技术栈：五阶段SDLC(Spec→Design→Plan→Build→Evolve) / 4 Sub-Agent(implementer/code-reviewer/feedback-observer/evolution-runner) / 11 Skills / 6 Hooks(PreToolUse/PostToolUse/UserPromptSubmit/SessionStart/Stop) / DAG并行Phase调度 / Sub-Agent隔离 / 验证即证据门禁 / Markdown Spec+Plan / MCP Design-to-Code / feedback进化引擎。
关键效果：从0到1产品交付周期压缩50%+，代码质量通过两阶段审查+四步走验证保证，团队经验通过进化引擎持续沉淀为规则，新人上手从2周缩短到3天。
面试话术：Agent Harness不是针对AI Agent开发的，而是一套完整的软件开发全生命周期工程框架，跑在Claude Code之上。核心架构分五层：主控层（CLAUDE.md）定义角色和流程路由；Sub-Agent调度层派发4个专用Agent（implementer负责编码、code-reviewer负责两阶段审查、feedback-observer静默记录反馈、evolution-runner扫描进化信号）；Skills能力层封装了11个可调用Skill，覆盖从需求收集(product-spec-builder)到发布(release-builder)的完整链路；Hooks事件层挂载6个脚本在PreToolUse/PostToolUse/UserPromptSubmit等生命周期事件上，自动做编译检查、端口清理、反馈检测、自动推送；进化引擎层四层递进——feedback静默记录→3+次出现自动提议规则毕业→Skill评分低提议优化→新模式5+次提议创建新Skill。

开发时核心流程是五阶段SDLC：Spec（product-spec-builder通过追问生成完整需求文档）→Design（design-brief + design-maker通过MCP对接Pencil/Figma出设计稿）→Plan（dev-planner按无占位符原则拆分为原子化Phase和Task）→Build（dev-builder驱动per-Task实现循环：编码→自检→派发code-reviewer两阶段审查→修复→commit，全部Task完成后执行四步走Phase验证）→Evolve（进化引擎自动沉淀经验）。

三大工程纪律铁律：验证即证据——每个完成声明必须现场附上新鲜验证输出，不接受"之前测过了"；Sub-Agent隔离——每个Task一个fresh实例，不继承session历史，防止Task A的错误假设污染Task B；反合理化清单——预定义AI最容易跳过规则的借口和正确做法（"这个很简单直接写就行"→"Plan Mode不看复杂度看纪律"）。

Hooks层是独特的自动化防线：detect-feedback-signal.sh在UserPromptSubmit事件中检测用户是否在纠正AI（匹配"不是这样""搞错了""你漏了"等30+种模式），命中时注入信号强制派发feedback-observer；pre-commit-check.sh在git commit前自动跑tsc --noEmit，编译不通过阻止提交；auto-push.sh在commit后自动推送到远程。

关键坑有两个：一是早期per-Task review-fix循环的编译验证太宽松，允许"跳过tsc直接commit"导致问题后置，后来用pre-commit-check Hook硬性阻断才根治。二是进化引擎初期提议太频繁打扰用户，后来加了"occurrences≥3才提议、用户只确认不跳过"的收敛策略。
项目出彩部分：① 五层架构设计（主控→Sub-Agent→Skills→Hooks→进化引擎）——不是简单的流程文档，是一套可运行的工程化系统。② Sub-Agent隔离 + 验证即证据 + 反合理化清单三条铁律——解决了AI辅助开发中"看起来快了实际质量崩了"的核心矛盾。③ 6个Hook自动化防线——在PreToolUse自动编译检查、UserPromptSubmit自动检测修正信号、PostToolUse自动推送，零人工干预。④ 进化引擎四层递进——feedback→规则毕业→Skill优化→新Skill创建，框架越用越贴合团队。

Q1: Agent Harness和传统SDLC/敏捷开发有什么区别？它解决的是什么层面的问题？⭐⭐⭐▶

传统SDLC（瀑布/敏捷）解决的是"人与人之间的协作流程"——需求文档、Sprint规划、Code Review、上线审批。Agent Harness解决的是"人和AI之间的协作流程"——AI辅助编码时代，开发者的工作方式从"写代码"变成了"用自然语言描述需求→AI生成→人工Review"。传统流程有几件事管不了：第一，AI生成的代码质量参差不齐，传统Code Review没有自动化防线；第二，AI容易"跳过思考直接编码"，没有Plan Mode约束；第三，AI没有记忆，团队踩过的坑无法自动沉淀为规则。

Harness把这套管起来了。核心分五层：主控层定义AI的行为准则；Sub-Agent层派发implementer和code-reviewer做per-Task的编码→审查→修复循环；Skills层封装了11个可调用模块（从product-spec-builder到release-builder覆盖完整链路）；Hooks层在PreToolUse/PostToolUse等事件上挂载自动化守卫脚本；进化引擎层把用户每一次纠正静默记录为feedback，3次以上自动提议升级为正式规则。

打个比方：传统SDLC是"人→人"的协作规范，Harness是"人→AI"的协作规范。

→ 和LangSmith比呢？

性质不同。LangSmith是观测层——追踪运行时发生了什么。Harness是流程层——管的是开发时怎么做。两者可以互补：Harness控制开发流程，LangSmith提供运行时观测数据辅助决策。

Q2: Agent Harness的五阶段SDLC具体怎么运作？每个阶段的交付物是什么？⭐⭐▶

五阶段是Spec→Design→Plan→Build→Evolve，和传统SDLC不同的是每个阶段都有对应的Skill自动执行，且内嵌了工程纪律。

第一阶段Spec——调product-spec-builder，通过追问引导用户想清楚需求。不是用户说什么就记什么，是用追问（"这个功能真的需要吗""用户是谁""怎么衡量成功"）逼用户想清楚。输出Product-Spec.md。纪律是AI优先原则：遇到任何功能需求先判断能不能用AI做。

第二阶段Design——可选。design-brief-builder出视觉方向，design-maker通过MCP对接Pencil/Figma从设计工具读取精确的页面数值（宽高/padding/字号/颜色）。开发时每个Task前重新读取，不凭记忆编码。

第三阶段Plan——调dev-planner，按无占位符原则拆分为原子化Phase和Task。每个Task必须写明具体文件路径和交付内容。产出DEV-PLAN.md。核心纪律：可验证原则（每个Phase完成后必须能编译能运行）、依赖正序原则（地基先打房子后盖）、粒度适中原则（一个Phase对应1-3个可独立验收的交付物）。

第四阶段Build——调dev-builder，进入per-Task实现循环。每个Task：Plan Mode列TaskList→读设计稿数值→编码→自检→派发code-reviewer做两阶段审查（Stage 1 Spec Compliance→过了才进Stage 2 Code Quality）→不通过则修复→通过则commit。所有Task完成后执行四步走Phase验证（Code Review→测试完整性→tsc --noEmit编译验证→功能测试）+ 冒烟测试（安全扫描+密钥泄露+进程管理）。纪律：验证即证据——每次完成声明必须附现场编译输出。

第五阶段Evolve——由进化引擎自动驱动，不是传统的人为复盘。feedback-observer静默记录每次用户的纠正，evolution-runner扫描积累，occurrences≥3提议规则毕业，评分持续偏低提议Skill优化，新模式≥5次提议创建新Skill。用户确认后执行。

→ 这个五阶段和Scrum有什么区别？

Scrum解决团队协作节奏（Sprint/站会/回顾）。Harness解决"每个原子单元怎么做"——编码→自检→审查→修复→commit的循环，以及过程中不做无关改动。Scrum管宏观节奏，Harness管微观工程纪律。

→ 什么情况下可以跳过Design阶段？

没有视觉要求的项目（CLI工具、API服务、纯后端）可以跳过。但有前端界面的项目强烈建议至少走design-brief确定信息密度和视觉方向。如果连design-brief都没有，开发时UI全靠AI自由发挥，往往要返工。

Q3: Harness里的Prompt版本管理是怎么做的？⭐⭐▶

Prompt存在Git仓库里，每个Agent一个目录。改Prompt就是提交一个PR，PR里必须包含评测集对比结果——改了Prompt之后跑一遍评测，和上一个版本的分数做对比。分数提升了或者持平才能合并，分数下降就拒绝。

版本回滚很快，因为Prompt是文本文件，Git直接回滚到上一个commit就行，秒级。我们还做了一个小工具，能在Web界面里看到两个版本Prompt的diff，以及对应的评测分数变化，很直观。

→ Prompt和业务代码放在同一个仓库吗？

是的。这样版本号天然一致，发版时一起打包。但也有缺点——改Prompt也要走代码发布的流程，不能像MCP Prompt原语那样即时生效。权衡下来，我们更需要版本可追溯，所以选了Git-backed。

→ Prompt diff的可读性怎么保证？

YAML格式，每个段落一行，diff时能清楚看到哪段改了。长Prompt按功能分块——角色定义、约束条件、输出格式、示例，每块独立修改，diff比较清晰。

Q4: Harness里的质量门禁是怎么设计的？Per-Task审查、Per-Phase验证、评测红线这三层分别管什么？⭐⭐⭐▶

质量门禁分四层，每层在开发流程的不同节点介入，越靠里发现问题越早、修复成本越低。

Layer 1: Per-Task 2-Stage Review——这是最细粒度的门禁。每个Task实现后，派发code-reviewer Sub-Agent执行两阶段审查。Stage 1验"做对了没有"（Spec Compliance）——对照Spec逐条功能确认是否已实现，有没有Scope Creep（代码中出现了Spec没写的功能）。Stage 1有HIGH priority问题就停在原地，不进Stage 2。Stage 2才验"做好了没有"（Code Quality）——命名规范、类型安全、无any、无硬编码密钥。两个Stage都通过才能commit。这层的设计哲学是先确保做对的事，再追求做事的质量，顺序不能反。

Layer 2: Per-Phase 四步走验证——所有Task完成后执行：① Code Review（对照Phase交付清单逐项确认）→ ② 测试完整性（功能清单打勾）→ ③ 编译验证（tsc --noEmit零错误）→ ④ 功能测试（启动dev server验证+冒烟）。这层关注的是跨Task的集成问题——导入关系对不对、文件依赖有没有环、命名一致性。

Layer 3: 冒烟测试——安全扫描（npm audit无critical漏洞）、密钥泄露检查（代码中无硬编码API Key/Token）、进程管理（只有1个dev server实例在运行）。

Layer 4: 业务评测红线——这是项目实例化的配置层，不是框架本身的通用门禁。每个Agent配置200-500个评测case，跑CI时自动评测，输出意图识别准确率、回复相关性、幻觉率等指标。我们采用总分加权+关键场景保底+异常波动检测三层保护，防止一个边界case波动卡死发布。

核心思路是：越内层的门禁越自动化、越早发现问题、越通用；越外层的门禁越贴近业务语义、越晚介入、越需要人工判断。

→ 评测集是怎么构建的？

三部分：人工标注的典型场景（占40%）、线上捞的真实对话（占40%）、边界和对抗case（占20%）。真实对话按客户满意度筛选，只保留评分4分以上的。对抗case专门用来测试模型的鲁棒性，比如故意输入错别字、语序混乱的句子。

→ 评测集会不会过拟合？

会。我们遇到过Prompt在评测集上表现很好，但上线后真实用户的表现一般。后来发现是因为评测集里有些case和Prompt里的示例太像了。现在的做法是每月更新一次评测集，替换掉30%的老case，加入新的线上样本。同时做新旧隔离——替换下来的老case存到退役评测集里，定期跑回归测试。

Q5: Agent Harness和Dify/Coze这类低代码平台是什么关系？会替代它们吗？⭐⭐⭐▶

不是替代关系，是互补。Dify和Coze解决的是"用什么工具"——它们提供可视化的工作流编辑器、预置的模型接口、现成的RAG组件。Harness解决的是"怎么开发"——定义了从需求到发布的标准流程和质量标准。

在我们的团队里，非技术背景的产品经理用Dify快速搭建原型验证想法；验证通过后再交给工程师，用Harness规范化的流程做工程化改造——补评测集、过质量红线、写设计文档。两个阶段用不同的工具，但Harness管住了"不能随便把一个没验证的Dify工作流直接推到生产环境"。

→ 如果团队用Dify做的Agent，Harness怎么统一管理？

Dify导出的配置可以转成Harness的Intent Spec。评测集和红线检查是通用的，不管底层用的是Dify还是自研代码。我们在Harness里做了适配层，支持导入Dify的Prompt和评测结果。

Q6: Agent Harness落地后，团队的开发效率和质量有什么变化？⭐⭐▶

几个数据。开发周期从平均2周缩短到3天——因为流程标准化了，Intent Spec模板和设计Review清单让需求澄清更快，不用反复确认。生产事故从每月3-4起降到0-1起——质量红线拦截了大部分有问题的发布。Prompt迭代周期从2天缩短到半天——Git-backed的版本管理和自动评测让试错成本大幅降低。新人上手从2周缩短到3天——有Pattern库和Anti-pattern清单可以参考。

→ 这些指标是怎么统计的？

开发周期看JIRA的Story周期时间；事故看飞书值班群的告警记录；迭代周期看Git提交到评测通过的时间；新人上手看试用期导师的评估反馈。数据不是100%精确，但趋势是明显的。

→ 效率提升有多少能归因于Harness本身？

很难完全归因。团队同时也在成长，成员对业务更熟悉了。但Harness的贡献是可以感知的——最明显的是事故减少，这个和Harness的质量红线直接相关。开发周期缩短有一部分是因为流程标准化减少了沟通成本，这个也是Harness的核心价值。

Q7: Harness里的Pattern和Anti-pattern库是怎么沉淀的？⭐▶

有两种沉淀路径，手动和自动。

手动路径——每次项目复盘时，我们会梳理哪些做法效果好、哪些做法踩了坑。效果好的提炼成Pattern（"查轨迹场景先确认运单号，避免模糊查询"），踩坑的提炼成Anti-pattern（"不要把业务规则写在Prompt里，规则变化时要改Prompt"）。目前沉淀了30个Pattern和20个Anti-pattern，分架构层、设计层、实现层三层粒度。

自动路径通过进化引擎——feedback-observer sub-agent在后台静默记录每次用户的纠正和反馈，不打断工作流。evolution-runner定期扫描积累的feedback，识别三类进化信号：当同一个问题出现3次以上，自动提议规则毕业（升级为SKILL.md或CLAUDE.md中的正式规则）；当某个Skill的反馈评分持续偏低，提议Skill优化；当某个操作模式反复出现5次以上但无Skill覆盖，提议创建新Skill。所有提议需要用户确认后才执行，不会自动改规则。

这套机制保证框架越用越贴合团队——开发三个月后的Harness和刚开始的Harness是不一样的：经过feedback冲刷后，团队特有的Pattern会自动沉淀为正式规则。

→ Pattern的粒度是什么样的？

分三层：架构层（比如"多Agent共享底层服务用MCP"）、设计层（比如"状态机管流程，LLM管回复"）、实现层（比如"Prompt里用YAML格式方便diff"）。新人一般先看架构层和设计层，实现层在写代码时查。

→ 自动沉淀和手动沉淀的比例大概多少？

初期手动为主（70%），三个月后自动沉淀的比例逐步提升到50%左右。因为刚起步时feedback积累不够，进化引擎没信号。跑起来之后，一些重复性反馈会自动触发规则升级建议，团队只需要确认或跳过。

Q8: 如果让你重新设计Agent Harness，你会做哪些改进？⭐▶

有几个方向。第一是做可视化编辑器，现在写Intent Spec和评测集都是写YAML，对非技术背景的产品经理不够友好。如果能像Dify那样拖拽配置，更多人能用起来。

第二是增加更全的静态检查——现在主要是跑评测集，但 Prompt 里有没有潜在的安全问题（比如提示词注入）、有没有逻辑矛盾，这些在运行前就能检查出来。第三是做跨项目复用——比如一个Agent的评测集可以继承另一个Agent的，只需要增量补充。第四是增加AI特有的质量指标，比如幻觉率、指令遵循率，这些传统软件没有的指标。

→ 幻觉率怎么衡量？

用LLM做裁判——把Agent的回复和RAG检索结果一起喂给一个专门的评估模型，让模型判断回复里有没有超出检索结果的事实。这个方案成本比较高，所以目前只在关键业务Agent上跑，不是所有Agent都测。

Q9: Harness的五阶段流程具体是怎么压缩开发周期的？能不能拆解每个阶段的收益？⭐⭐▶

整个五阶段流程里，时间压缩最多的是 Intent Spec 和 Implementation 两个阶段。

Intent Spec 模板化之前，产品经理提需求的方式是写一页文档或者直接口头说，工程师要反复确认才能把模糊的需求变成可执行的任务。经常出现"需求理解偏差，开发到一半发现场景不对"的情况，来回沟通就要 2-3 天。有了 Intent Spec 模板（目标、用户画像、Top 5 场景、边界、成功指标），产品经理填完模板，工程师直接 Review，理解偏差少了很多，需求澄清从 2-3 天缩短到半天。

Implementation 阶段的压缩来自 Pattern 库和 Anti-pattern 库。新 Agent 开发的基本框架（Prompt 结构、评测集格式、CI 配置）都是现成的模板，不用从零搭。加上 30 个 Pattern 覆盖了常见场景的最佳实践，工程师照着写就行，不用每种场景都重新设计。代码实现从原来的 1 周左右压缩到 1-2 天。

Verification 阶段用自动评测替代了原来的人工测试。原来改完 Prompt 要找业务同学手动验证，等别人有空就要半天一天。现在 CI 自动跑，20 分钟出结果，没过直接被阻断，不用等人。

综合下来，开发周期从 2 周压到 3 天，核心是"减少沟通等待、减少重复设计、减少人工验证"。

→ 这五个阶段里哪个阶段最容易成为瓶颈？

Verification 阶段。如果评测集比较弱，跑出来的分数虚高，上线后才发现问题，回头补评测集又要时间。所以我们在前期就要求评测集必须覆盖核心场景和边界 case，避免"评测集过弱→上线出问题→补评测集→重新发布"这个恶性循环。

→ 有没有阶段被跳过的情况？

有过。紧急修复线上事故的时候，Design Review 会被跳过，直接修完验证上线，事后再补。但我们有红线：不管多紧急，Verification 评测集不能跳，质量红线不能跳。Intent Spec 可以后补，但评测不通过不能上。

Q10: 团队用了Harness之后，多个Agent并行开发的时候怎么管理的？会不会互相阻塞？⭐⭐▶

Agent Harness 的设计前提就是"多个 Agent 并行开发，互不阻塞"。每个 Agent 有独立的 Intent Spec、独立的评测集、独立的 Git 目录和 CI 流水线，A Agent 改了 Prompt 不会触发 B Agent 的评测。

真正需要协调的是共享资源——MCP Server 的接口变更、底层模型的升级、Prompt 模板的调整。比如模型升级了，所有 Agent 的评测集都要重新跑一遍，确保没有回归。这个我们在 Harness 里做了"批量重评测"功能——模型升级时一键触发所有 Agent 重跑评测，哪几个 Agent 的分数降了、降了多少、是不是模型本身的问题，一目了然。

→ 如果 A Agent 改了一个共享 Prompt 模板，导致 B Agent 的评测分数下降了，怎么处理？

共享模板的变更也要走 PR 流程，PR 描述里必须写明"这个变更对哪些 Agent 有影响"，CI 自动拉出所有依赖这个模板的 Agent 评测结果对比。如果 B 的分数降了，PR 会被阻断，提交者需要协调 B 的负责人一起看看是改模板还是调 B 的 Prompt。

→ 并行多了会不会有"评测集 CI 排队"的问题？

初期有过。多个 Agent 同时提交，CI 排队要等。后来把 CI runner 从 1 台扩到了 3 台，加上评测是纯计算任务，没有外部依赖，可以水平扩展。现在基本不排队。

Q11: 质量红线从"单项必过"改成"总分加权"之后，有没有出现过某单项特别差但总分过了，导致线上出问题的情况？⭐⭐⭐▶

发生过一次，也是因为这个才进一步完善了权重设计。

有一次一个同事优化了 Prompt，评测集里意图识别、回复相关性、幻觉率三个指标的加权总分过了红线，但上线后发现"投诉处理"这个场景的回复相关性分数从 90 降到了 60，只是因为这个场景在评测集里 case 比较少（只占 5%），被其他场景的高分拉平了总分。

后来我们加了两层防护。第一层是"关键场景保底"——每个核心场景（投诉、理赔、改地址等）单独设最低分，即使总分过了，某个关键场景低于阈值照样阻断。第二层是"异常波动检测"——自动比对每个 case 的新旧版本分数，如果某个 case 分数下降超过 15 个百分点，即使总分过线也要人工确认才能放行。

这个教训告诉我们：总分加权解决的是"1% 的边界 case 波动不应该阻碍 99% 的正确改进"这个问题，但要做好配套的异常检测，防止"1% 的关键场景崩了被 99% 的一般场景掩盖"。

→ 权重的具体分配是怎么定的？

意图识别准确率 40%、回复相关性 30%、幻觉率 20%、平均延迟 10%。权重是根据业务影响定的——意图错了后面的流程全错，所以权重最高；幻觉影响客户信任但可以通过 RAG 限制缓解；延迟只要在红线内就行。每季度根据线上运行数据微调一次。

→ 异常波动检测的阈值 15% 怎么来的？

经验值。我们看了历史数据，正常迭代中 case 分数的波动一般在 ±10% 以内，超过 15% 说明要么这个 case 有特殊问题，要么改动影响面比预期大。低于 15% 的误报率太高。

Q12: Agent Harness的评测集是怎么保持新鲜度的？线上的真实数据怎么回流到评测集里？⭐⭐▶

评测集每月更新一次，替换掉 30% 的老 case。新 case 的来源有三个：

第一是线上真实对话。从日志里捞取样本，按客户满意度分层——满意度 4-5 分的高质量对话作为正样本，满意度 1-2 分且触发过转人工的作为负样本。人工标注团队每周处理大概 100 条，标注维度包括：意图识别是否准确、回复是否完整、是否有幻觉。

第二是运营反馈。客服运营同学每周提交他们遇到的"奇怪问题"——客户问法很偏、模型没理解对的。这些往往是最有价值的边界 case，覆盖了评测集没想到的场景。

第三是新业务场景。业务上线新功能时（比如新增了一种赔付类型），对应的评测 case 必须在上线前补充到评测集里，否则现有评测覆盖不了新场景。

→ 评测集每月更新 30%，怎么防止过拟合和评测集泄露？

两个机制。一是新旧隔离——替换下来的老 case 不删除，存到"退役评测集"里，定期用退役集跑回归测试，确保模型在新评测集上表现好了，在退役集上没有明显退化。二是相似度去重——新 case 和现有 Prompt 示例做 Embedding 相似度检查，相似度超过 0.95 的丢弃，防止 Prompt 里的示例和评测 case 过于相似导致模型"背答案"。

→ 人工标注的质量怎么保证？

抽检。标注后的数据随机抽 20% 做二次审核，标注准确率要求 95% 以上。低于这个阈值就退回重新标注。

Q13: 你们用AI辅助开发Agent的过程中（也就是vibe coding），遇到过哪些坑？⭐⭐⭐▶

我们团队在推行 Agent Harness 的过程中确实深度用了 AI 辅助编码，踩了不少坑，主要分三类。

第一类：AI 生成的 Prompt 看起来面面俱到，但边界 case 一碰就碎。典型症状是——让 AI 写一个客服 Prompt，它会把常见场景（查轨迹、问时效、改地址）的回复写得特别详细，但遇到训练数据里没见过的问法（比如"我的货在分拨中心停了，但我明天要去外地，能不能改到自提点"——这是查轨迹+改地址+时效预测的复合场景），模型就崩了。因为 AI 生成的 Prompt 倾向于"覆盖已知场景"而不是"约束模型行为边界"。后来我们总结了一个原则：Prompt 的核心不是告诉模型"要做什么"，而是告诉模型"不要做什么"和"不确定的时候怎么办"。这个原则是从吃了几次亏之后才提炼出来的。

第二类：AI 辅助生成的评测集质量参差不齐。AI 生成评测 case 很快，你给它 10 个种子 case，它能扩成 200 个。但问题在于这些 AI 生成的 case 往往是"同义改写"而不是"新场景扩展"——写了 200 个 case，实际覆盖的还是那 3 个场景，只是换了个说法。我们一开始没意识到这个问题，评测集看起来 500 个 case 很多了，但场景覆盖度很低，导致 Prompt 过拟合严重——评测集上 95 分，上线后真实场景 60 分。后来我们用 Diversity Score（基于 Embedding 的聚簇分布）来评估评测集的场景覆盖度，要求覆盖度不低于 80% 才能通过。

第三类：AI 生成代码时的"过度抽象"问题。AI 倾向于生成非常"优雅"的代码——工厂模式、策略模式、多层继承。但 Agent 的 Prompt 逻辑往往需要频繁调整，过度抽象反而增加了修改成本。比如 AI 把一个很简单的"意图识别→路由"逻辑抽象成了 RouterFactory + StrategyRegistry + IntentHandler 三层，改一个路由规则要改三个文件。后来我们在 Pattern 库里加了一条硬性规定：Agent 开发优先写平铺直叙的代码，只在确实需要复用的地方做抽象。

→ AI 自动生成的评测 case 和人工标注的评测 case 效果差距有多大？

差距不小。人工标注的 case 往往包含真实业务中的"脏数据"——比如客户说话带口头禅、语法不通顺、有错别字。AI 生成的 case 太干净了，测试不出模型的鲁棒性。我们的经验是 AI 生成的 case 适合做"数量补充"，人工标注的 case 必须占 40% 以上，否则评测集会有偏差。

→ 怎么防止工程师过度依赖 AI 导致代码质量下降？

Harness 的质量红线本身就是一道防线——AI 生成的代码如果不能通过评测集，再快也没用。另外 Code Review 时会重点关注"这段代码里有没有 AI 生成的不相关逻辑"，比如 AI 经常自作主张加一些"未来可能会用到"的校验和降级策略，这些在 Review 时会被剪掉。简单说就是：AI 负责写，人负责删。删比写更重要。

Q14: Vibe coding在Agent开发场景下，边界在哪？什么适合让AI做、什么必须人来做？⭐⭐⭐▶

我们的实践经验总结了一个"三做三不做"的边界。

适合让 AI 做的三件事：
1. Prompt 初稿生成——给定需求描述让 AI 生成第一版 Prompt，效率很高。但要人工 Review 边界 case 覆盖度。
2. 评测 case 批量扩写——人工写 20 个种子 case，AI 扩到 200 个，效率提升明显。但要人工标注覆盖真实脏数据。
3. 模板代码和测试脚手架——YAML Schema、CI 配置、单元测试模板，这些有固定模式适合 AI 写，Review 负担小。

不适合让 AI 做的事三件事：
1. 质量红线决策逻辑——哪些指标设红线、阈值多少、权重怎么配，这些涉及业务风险和团队经验，AI 没有上下文，容易给出"技术上正确但业务上危险"的建议。
2. 评测集的关键场景设计——哪些场景是核心场景、边界 case 的边界在哪，需要业务知识，AI 生成的往往是通用场景，漏掉业务特有的长尾 case。
3. 容灾降级策略——LLM 挂了怎么兜底？RAG 挂了怎么处理？这些涉及系统架构和业务连续性，AI 生成的方案往往太理想化，没考虑到真实环境中各种组件的实际依赖关系。

核心判断标准就一条：有明确的"对错标准"且边界清晰的事适合 AI，需要权衡风险或涉及业务判断的事必须人做。 Prompt 可以给 AI 写，但"这个 Prompt 能不能上线"是人的事。

→ 如果新人来了直接让 AI 写 Agent，不走 Intent Spec 和 Design Review，会有什么问题？

我们踩过这个坑。新人觉得"跟 AI 聊聊天就能出代码，为什么要写 Spec 那么麻烦"。结果写出来的 Agent 在简单场景上跑得挺好，但一问到"这个 Agent 的边界是什么""哪些场景不做""失败时怎么处理"，完全答不上来——因为 AI 帮他写的代码只覆盖了正常流程，异常路径一个都没处理。

后来我们的 onboarding 流程改了：新人前两周不允许直接用 AI 写 Agent 代码，必须手写一个完整的 Agent（包括 Intent Spec、Prompt、评测集），目的是理解"一个 Agent 需要定义什么"。两周之后再用 AI 加速。这个门槛过了之后，AI 才能成为工具而不是拐杖。

Q15: Agent Harness在多团队协作下，怎么防止各自为政？⭐⭐▶

这是个很实际的问题。Harness 解决了"有没有流程"的问题，但不能保证每个团队"按同一个标准执行流程"。我们做了三层统一。

第一层是强制模板。 Intent Spec 模板、评测集格式、CI 配置模板都是统一的，每个新 Agent 项目初始化时从模板仓库 fork，不允许自己从头写。这样即使不同团队开发的 Agent，基础结构是一致的，Review 的时候不用重新理解别人的格式。

第二层是 Shared Pattern 库。所有团队共用一个 Pattern 和 Anti-pattern 库。A 团队发现了一个好做法，提炼成 Pattern 提交 PR，Review 通过后所有团队都能看到。B 团队踩了一个坑，提炼成 Anti-pattern，其他人可以避免。这个库是"众筹"的，不是自上而下规定的，所以团队接受度高。

第三层是 Gardener 角色。每个 Sprint 轮值一个"质量守护者"（Gardener），负责抽查本周提交的所有 Agent 变更（哪怕通过了 CI）。主要看：Prompt 有没有明显的反模式、评测集补充是否合理、边界 case 覆盖够不够。这个角色不是"审计"而是"教练"——发现问题不是罚款，而是和开发团队一起改进。这样既保证了质量一致性，又不会变成官僚流程。

→ 不同团队对质量红线的接受度一样吗？

不一样。语音客服团队对稳定性要求极高，觉得我们的红线太松；新业务探索团队觉得红线太严，经常阻碍快速试错。我们的解法是"核心红线 + 弹性红线"两层：核心红线（幻觉率、准确性）所有团队必须过，弹性红线（延迟、Token 消耗）新业务可以申请豁免，但要写明豁免原因和预计什么时候达标。这样既保证了底线质量，又给创新留了空间。

→ Gardener 制度推行起来有阻力吗？

初期有。"为什么要别人来 Review 我的代码？"团队有抵触。后来我们做了两个调整：一是 Gardener 轮值，每个人都要当，每个人也要被别人查，公平；二是 Gardener 不阻断发布，只提建议，最终决策权在开发团队自己。推行一个 Sprint 之后大家发现 Gardener 确实能帮自己发现盲区，接受度就高多了。

AI Agent 高频面试题

Q1: 现在常见的Agent架构模式有哪些？跨越速运的项目里是怎么选的？⭐⭐⭐▶

四种模式用得比较多。ReAct是最基础的——模型想一步做一步，适合简单任务，比如查个轨迹、回答个常见问题。Plan-and-Execute是先做规划再做执行，适合复杂任务——比如客户说"帮我查一下这批货为什么延误了，顺便改个地址"，需要先拆解成查轨迹、分析原因、改地址三个子任务。Reflection是自检模式，生成回复后再让模型检查一遍有没有问题，适合对质量要求高的场景。Multi-Agent是多个Agent分工协作，我们MCP集群其实就是这种思路——不同业务线的Agent共享底层服务。

跨越速运的项目里没有用某一种模式包打天下，而是按场景选。语音客服的对话管理是状态机+ReAct混合，异常处理是Plan-and-Execute，评测环节用了Reflection。

→ ReAct的循环怎么控制？会不会无限循环？

会，所以要设上限。我们配了最大轮数5轮，超过5轮还没结束就强制退出，走兜底话术。还有一个防重复机制——如果模型连续两次想调用同一个Tool且参数完全一样，就判定为循环，直接退出。

→ Plan-and-Execute里规划失败怎么办？

如果规划出来的子任务有依赖循环或者不可执行的步骤，会触发重新规划。最多重试3次，3次都失败就降级到ReAct模式，让模型边想边做。

Q2: 一个物流知识库，用RAG、微调还是长上下文？怎么选？⭐⭐⭐▶

这三个不是互斥的，而是各有分工。RAG管"知识"——物流时效、运费规则、网点信息这些经常变的东西，放RAG里更新最快，改个文档就行，不用重新训练模型。微调管"风格"——模型说话的方式、对物流术语的理解、客服话术的规范性，这些通过微调内化到模型里。长上下文管"一次性大文档"——比如客户发了一个Excel表格里面几十条运单，需要一次性处理。

跨越速运的实践是"微调管风格、RAG管知识"。客服对话风格通过微调内化，产品知识通过RAG动态检索。长上下文我们目前用得比较少，主要是客服场景里很少有一次性几十条运单的情况。

→ RAG和长上下文能结合吗？

可以。对于特别大的知识库，先用RAG粗召回相关的Top-K文档，然后把这K个文档塞到长上下文窗口里让模型精读。这样既能处理海量知识，又能利用长上下文的精准理解能力。不过成本会比较高，需要权衡。

→ 成本上哪个最高？

长上下文最高。一次性塞几万token，推理成本是线性增长的。RAG的成本主要是检索，推理时只带少量相关片段。微调的成本是训练时一次性支出，推理时和基础模型一样。所以日常查询RAG最便宜，微调是一次性投入，长上下文要谨慎用。

Q3: RAG检索效果不理想的时候，你们会怎么优化？⭐⭐⭐▶

RAG优化我们走过一个完整的路径。最开始用纯向量检索，发现客户问"我的快递在哪"和"我的货到哪了"其实是同一个问题，但向量相似度不高，检索会漏。后来改成了混合检索——同时走稠密向量（语义理解）和稀疏向量（关键词匹配），两条路的结果合并，覆盖率提升了不少。

第二步加了Rerank。粗召回Top-20之后，用一个轻量模型做二次排序，把最相关的排到前面。Rerank对语音场景特别重要，因为ASR转出来的文本可能有误差，直接用向量相似度排序不太靠谱。

第三步做了Query改写。用户问"上次那个件"，模型不知道"上次"和"那个"指什么。我们在检索前加了一步——用LLM把用户的模糊表述扩展成明确的查询语句，比如把"上次那个件"改写成"运单号XXX的货物"（从上下文提取运单号）。

→ Rerank用的是Cross-Encoder还是Bi-Encoder？

Cross-Encoder。虽然慢一点，但精度高。Bi-Encoder适合粗召回，Cross-Encoder适合精排。我们的Rerank模型大概100ms能排20个文档，延迟可以接受。

→ Query改写是每次都做吗？

不是。只有检测到query里有指代词（"那个"、"上次"）、时间模糊词（"最近"）、或者语义不完整时，才触发改写。完整明确的query直接走检索，省掉改写这一步的延迟。

Q4: 多Agent协作有哪些模式？跨越速运是怎么做的？⭐⭐▶

两种主流模式。中心化模式是一个主Agent负责调度，多个子Agent负责执行——主Agent分析用户意图，决定调用哪个子Agent。去中心化模式是Agent之间直接通信，比如A2A协议，每个Agent既是服务提供者也是消费者。

跨越速运用的是"共享服务"模式，更接近中心化。底层能力（RAG、记忆、Prompt模板）封装成MCP Server，所有业务Agent共享。好处是能力复用、统一管理；坏处是如果底层服务挂了，所有Agent都受影响。

→ A2A协议和MCP有什么区别？

A2A是Agent之间的通信协议，MCP是Agent和工具之间的协议。A2A解决的是"Agent A怎么调用Agent B"，MCP解决的是"Agent怎么调用RAG检索"。两者不冲突，可以一起用。

→ 多Agent通信的延迟怎么解决？

同步调用链太长的话延迟会累积。我们的做法是：语音客服这种对延迟敏感的用本地编排，不走网络；LangGraph异常处理这种异步场景走HTTP调用，延迟不敏感。底层MCP Server部署在同一可用区，内网通信延迟在10ms以内。

Q5: 物流客服场景下，怎么控制模型幻觉？⭐⭐⭐▶

四层防护。第一层是RAG限制——所有产品知识必须从RAG检索结果里来，不允许模型凭记忆瞎编。我们在Prompt里明确写了"如果你不知道，就说不知道，不要猜测"。第二层是Tool验证——模型生成的运单号、手机号必须调用验证接口确认存在，不存在就拒绝回复。第三层是结构化输出——让模型输出JSON而不是自由文本，限制它的发挥空间。第四层是人工兜底——高风险操作（比如修改地址、发起赔付）必须人工确认。

→ 有没有发生过比较严重的幻觉事故？

有一次模型把"预计明天到达"说成了"明天一定到达"，结果第二天因为天气原因延误了，客户非常生气。后来我们发现是因为Prompt里的措辞不够严谨，模型学会了用"一定"这种绝对化表述。修复方案是在Prompt里加了语气约束——"描述时效时用'预计'，不要用'一定'、'肯定'"。

→ 结构化输出和自由文本的效果差距大吗？

在客服场景里，结构化输出的可控性明显更好，但自然度稍差。比如自由文本可以说"您的快递预计明天到达，建议您保持电话畅通"，结构化输出可能变成冷冰冰的JSON字段。我们的折中方案是：内部处理用结构化，最终回复时再用模板渲染成自然语言。

Q6: AI系统的可观测性怎么做的？和传统系统有什么区别？⭐⭐▶

AI系统的可观测性比传统系统多了一个维度——"模型在想什么"。传统系统看日志就知道哪里出错了，AI系统可能日志里一切正常，但模型输出了胡说八道的内容。

我们做了四层。第一层是LangSmith追踪，记录每次LLM调用的输入输出、Token消耗、延迟。第二层是结构化日志（structlog），每条日志带request_id，全链路可追踪。第三层是指标监控——意图识别准确率、幻觉率、客户满意度，这些业务指标比系统CPU内存更重要。第四层是成本追踪——每个Agent每天花多少Token、多少钱，超出预算告警。

→ structlog和Python自带的logging有什么区别？

structlog输出的是结构化JSON，方便机器解析和检索。Python logging默认是文本，想从日志里提取字段很麻烦。我们所有服务统一用structlog，日志直接打到ELK里，排查问题时可以用Kibana做过滤。

→ Trace采样率怎么设的？全量采集成本太高了吧？

错误请求100%采集，成功请求10%采样。这样既不会漏掉错误，又能控制成本。LangSmith本身也有配额限制，我们按团队分配额度，超了就降级到自研的简易追踪。

Q7: 做AI项目时，大模型选型会考虑哪些维度？跨越速运是怎么选的？⭐⭐▶

四个维度。延迟——客服场景TTFT必须控制在3秒以内，简单任务走轻量模型。成本——每天几十万次调用，Token单价差一分钱，月成本就差几万。推理能力——复杂异常处理需要强推理能力，简单查询用轻量模型就够了。上下文长度——有些场景需要带长历史对话，要求上下文窗口足够大。

跨越速运的策略是"分层路由"。简单意图走doubao-lite，延迟低成本低；复杂意图走doubao-pro，推理能力强。不追求用一个模型解决所有问题，而是按场景分配资源。

→ 不同厂商的模型怎么对比？

用评测集跑分。我们建了一个中立的评测平台，同一套评测集在多个模型上跑，对比延迟、成本、准确率三个指标。选模型不是选最好的，是选"满足质量要求的前提下成本最低"的。

→ 上线前会做A/B测试吗？

会。小流量5%跑一周，对比新旧模型的业务指标。不仅看准确率，还要看客户满意度、对话轮数、问题解决率。有一次新模型准确率提升了2%，但客户满意度反而下降了，后来发现是因为新模型回复太啰嗦，客户不耐烦。

Q8: Token成本优化有哪些手段？在跨越速运的体量下效果如何？⭐⭐▶

五个手段。模型路由——简单问题走轻量模型，成本差10倍。Prompt精简——System Prompt从800token压到200token，Prefix Caching命中率从40%提升到75%。Max Token分级——不同场景给不同的输出上限，避免浪费。RAG片段压缩——检索结果去掉无关段落，只保留核心句子。缓存——常见问题的回答直接走缓存，不走模型。

综合下来，单请求平均Token消耗降低了60%，月度成本从15万降到6万左右。关键是这些优化都没有牺牲质量——路由错误率控制在5%以内，Prompt精简后评测分数基本持平。

→ 成本降了60%，对回复质量有影响吗？

评测指标没有明显下降，但有个隐性影响——Prompt精简后，模型在某些边界case上的表现稍微弱了一点。我们在评测集里补充了更多边界case，确保精简后的Prompt覆盖度足够。

Q9: AI系统的安全和权限控制怎么做？⭐⭐▶

四层防护。第一层API Key+配额——每个项目独立的Key，用完配额就限流，防止资源被耗尽。第二层project_id隔离——RAG检索、用户画像按项目隔离，A项目查不到B项目的数据。第三层Tool授权——不是每个Agent都能调用所有Tool，敏感操作比如"修改地址"需要额外授权。第四层高风险人工确认——赔付、退款这些操作，金额超过阈值必须人工确认。

Prompt层面也有防护——在System Prompt里加了安全约束，比如"不要生成代码"、"不要透露系统内部信息"、"不要回答与物流无关的问题"。

→ 有没有遇到过越权访问的情况？

有一次测试环境的Agent误用了生产环境的API Key，好在测试环境的project_id和生产环境不一样，RAG检索返回空结果，没有造成数据泄露。后来我们加了环境隔离——不同环境的Key前缀不一样，代码里做了校验。

→ 怎么防止Prompt注入攻击？

输入过滤+输出校验。用户输入先过一层过滤，检测到疑似注入的关键词（比如"忽略之前的指令"）就告警。输出层再校验，如果模型回复包含了不应该出现的内容，就拦截并返回兜底话术。

Q10: 长对话场景下上下文怎么管理？ ⭐⭐ ▶

三层管理。短期记忆存最近N轮对话，存在Redis里，TTL 30分钟。N根据场景动态调整——客服场景N=10，因为用户一般不会连续问太多问题；导购场景N=20，因为用户可能会反复比较不同产品。

超过N轮的历史做摘要压缩。用LLM把前面的对话提炼成关键信息——用户问了什么、我们回答了什么、有没有待办事项。摘要和最近的N轮一起送给模型，这样上下文不会无限增长。

长期画像存用户的偏好和历史行为，比如"这个客户经常投诉延误"、"这个客户偏好改配送到自提点"。画像不是每次对话都全量加载，而是按需查询——当前对话涉及到相关话题时才加载。

→ N具体怎么确定？

看历史数据统计。分析客服对话的平均轮数，取90分位数。跨越速运的客服对话90%在8轮以内结束，所以N=10足够覆盖绝大多数场景。

→ 摘要压缩会不会丢失关键信息？

会。有一次摘要把"客户要求加急"这个信息漏掉了，导致后续回复没有体现加急处理。后来我们在摘要模板里加了关键字段检查——必须包含"诉求"、"情绪"、"待办"三个字段，缺少任何一个就告警。

Q11: 多Agent协作中任务是怎么分解和分配的？跨越速运怎么做的？⭐⭐▶

任务分解和分配是多Agent协作的核心问题。主流有三种模式：静态路由——每个Agent负责固定领域，比如Agent A管查轨迹、Agent B管改地址、Agent C管投诉，由路由器根据用户意图分发；动态规划——由一个主Agent（Orchestrator）分析任务复杂度，动态拆分子任务并分配给不同子Agent，子Agent完成后结果汇总；竞争选举——多个Agent同时处理同一个任务，选一个最好的结果返回。

跨越速运用的是静态路由+动态规划的混合。日常高频场景（查轨迹、问时效）走静态路由，意图识别后直接分给对应的Agent，延迟最低。复杂场景（比如"我的货延误了，帮我查一下原因再改个地址"）走动态规划，由主Agent拆成"查轨迹→分析延误原因→改地址"三个子任务，分别调用不同的子Agent，最后汇总结果生成统一回复。

→ 子任务之间如果有依赖关系怎么办？

用DAG（有向无环图）描述依赖。比如"改地址"依赖"查轨迹"的结果（需要知道当前货物在哪才能判断能不能改地址），这两个任务就不能并行。主Agent在拆任务时会构建依赖图，按拓扑序执行。LangGraph的State机制很适合管这种依赖——每个子任务读写共享State，下游任务从State里读取上游结果。

→ 子任务执行失败了怎么回滚？

失败的子任务不会让整个流程崩掉，而是标记为失败并返回错误原因。主Agent根据错误类型决定：如果是临时错误（网络超时）就重试；如果是业务错误（地址不存在）就跳过该子任务，在最终回复里告知用户哪些操作完成了、哪些没完成。

Q12: 多Agent之间怎么共享记忆/状态？共享和独立怎么平衡？⭐⭐▶

多Agent的记忆分三层。第一层是全局共享状态——所有Agent都能读写的公共数据，比如当前对话的上下文、用户的运单号、已经确认过的地址。这层存在Redis里，TTL 30分钟，确保所有Agent看到的信息是一致的。第二层是Agent私有状态——每个Agent自己的中间结果，比如RAG Agent检索到的文档列表、代码生成Agent写的草稿代码。这层只在Agent内部流转，不共享。第三层是持久画像——用户的历史偏好和行为标签，存在PostgreSQL里，按需加载。

平衡的原则是"能私有不共享，必须共享才共享"。共享状态多了会引入竞争条件和一致性问题，而且如果一个Agent写错了数据，会影响所有下游Agent。所以设计上尽量让Agent通过输入参数传递数据，而不是读写共享变量。只有跨对话必须保留的信息（如用户身份、当前运单号）才放进共享状态。

→ 共享状态的并发写怎么解决？

用乐观锁。每个共享状态带一个version字段，Agent写入时检查version是否和读取时一致，不一致说明被其他Agent修改过了，需要重新读取再处理。LangGraph的Checkpointer本身有状态版本管理，天然支持这种冲突检测。

→ 不同Agent的上下文窗口都带全量历史吗？

不带。每个Agent只收到和它相关的上下文片段。比如改地址Agent只收到"用户要求改地址"和"当前地址"，不会收到之前查轨迹的详细结果。这样既能节省Token，又能避免无关信息干扰Agent的判断。

Q13: 多Agent协作出现冲突怎么办？比如两个Agent给出矛盾的结果。⭐⭐⭐▶

冲突有三种典型场景。第一种是事实冲突——Agent A说货物在北京，Agent B说货物在上海。解决方式是引入事实校验层，关键事实（如货物位置、运单状态）必须调用业务系统API确认，不以Agent的推理结果为准。第二种是策略冲突——Agent A建议赔付200元，Agent B建议赔付500元。解决方式是上层仲裁——由规则引擎或人工复核做最终决策，Agent只负责提供建议。第三种是资源冲突——两个Agent同时想修改同一个订单的状态。解决方式是加锁——修改前获取分布式锁，修改完释放。

我们在LangGraph里设计了"评审节点"——多个Agent并行输出结果后，由一个评审Agent（或规则引擎）做一致性检查。如果发现冲突，按优先级排序：业务系统数据 > 规则引擎 > 主Agent > 子Agent。最终输出必须明确标注数据来源，不确定的信息用"可能""建议"等措辞，避免给用户绝对化的承诺。

→ 评审Agent本身会不会出错？

会。所以评审结果只用于提示风险，不直接阻断流程。高风险冲突（如赔付金额差异超过1000元）必须人工复核；低风险冲突（如预计到达时间差半天）由评审Agent自动裁决并记录日志，后续人工抽查。

→ 怎么减少冲突的发生？

三个手段：一是职责边界清晰，每个Agent的Prompt里明确写"你只负责XXX，不要越界判断YYY"；二是数据源统一，所有Agent查货物状态都走同一个API，不从各自的记忆里瞎编；三是输入标准化，给每个Agent的上下文格式统一，减少理解偏差。

Q14: 多Agent架构和单体Agent（Single Agent）的选型边界是什么？⭐⭐▶

单体Agent适合任务单一、流程明确的场景——比如语音客服查轨迹，意图识别后直接调RAG检索，一个Agent就能搞定。多Agent适合任务复杂、需要多领域协作的场景——比如跨境合规审查，涉及单据解析、HS编码归类、规则审查、补单生成，每个子任务的专业性要求不同，用一个Agent做所有事效果会很差。

选型看三个指标：任务复杂度——如果任务能拆成3个以上独立的子任务，且子任务之间专业差异大，考虑多Agent。延迟敏感度——多Agent有通信开销，对TTFT要求<1秒的场景不适合。维护成本——多Agent的调试和评测更复杂，团队人手有限时优先单体Agent。

跨越速运的实践中，语音客服和在线客服是单体Agent（延迟敏感、任务相对简单），合规中台是多Agent（任务复杂、涉及多个专业领域），MCP集群是多Agent共享底层服务（多个业务Agent复用RAG、记忆等能力）。

→ 多Agent的通信开销有多大？

内网HTTP调用大概10-50ms，加上模型推理时间，一个3-Agent的协作链路总延迟大概在500ms-2秒。对异步场景（如合规审查）完全可接受，对实时场景（如语音客服）就需要权衡——要么合并Agent减少调用次数，要么用流式输出先给用户部分反馈。

→ 从单体Agent演进到多Agent的触发条件是什么？

通常是单体Agent的Prompt超过2000token、或者准确率遇到瓶颈、或者团队里有不同角色负责不同模块时。Prompt太长说明一个Agent承担了太多职责，拆成多个Agent每个Prompt更聚焦，效果往往更好。

Q15: Redis在AI系统里做什么？为什么选Redis而不是PostgreSQL/MongoDB？⭐⭐▶

跨越速运的项目里Redis主要做三件事。第一是短期会话记忆——用户和客服Agent的对话历史存在Redis里，按session_id隔离，TTL 30分钟。用户连续提问时，Agent从Redis里读出历史上下文拼进Prompt，保证对话连贯。第二是缓存——常见问题的RAG检索结果和LLM生成结果走Redis缓存，命中率高的时候能省掉大量Token成本。第三是限流和分布式锁——MCP网关用Redis做API配额限流，多Agent场景用Redis分布式锁防止资源冲突。

选Redis而不是PG/MongoDB的核心原因是延迟。会话记忆每次对话都要读写，Redis单节点延迟在1ms以内，PG即使走索引也要10ms以上，对话轮数多了差距很明显。而且Redis的TTL机制天然适合短期记忆——超过30分钟没新消息自动清掉，不用写定时任务。

PG负责长期画像和LangGraph Checkpointer这些需要持久化和事务支持的数据。MongoDB我们也考虑过，但团队对Redis更熟悉，且Redis的Sorted Set很适合做带过期时间的排行榜类需求（比如热门问题统计），所以没上MongoDB。

→ Redis挂了怎么办？记忆会丢吗？

Redis挂了短期记忆会丢，但设计上这不是致命问题。Redis只是加速层，丢了之后用户再发消息，Agent会把当前消息当新对话处理，不会崩。我们在Redis前加了本地Caffeine缓存做二级缓存，Redis挂了的短时间内（比如几秒），本地缓存还能撑一下。同时有哨兵模式做高可用，故障切换在10秒以内。

→ TTL 30分钟怎么定的？

看客服对话的间隔分布。统计发现95%的用户在两轮对话之间的间隔不超过20分钟，30分钟能覆盖绝大多数场景。设太短用户去喝杯咖啡回来上下文就丢了；设太长内存占用高。30分钟是平衡后的结果。

→ Redis和PG的数据一致性怎么保证？

短期记忆和长期画像互相独立，没有强一致性问题。对话结束后的画像更新是异步的——从Redis里读出完整对话，用LLM提取关键信息，然后UPSERT到PG。如果UPSERT失败会进死信队列，人工排查后重试。不要求实时一致，最终一致即可。

RAG 检索增强专题（高频面试题）

【架构类】RAG的完整流程是什么？每个组件有哪些选型？⭐⭐⭐▶

标准RAG流程分三个阶段：Indexing（索引）→ Retrieval（检索）→ Generation（生成）。

Indexing阶段：文档加载→ Chunk切分→ Embedding向量化→ 存入向量库。选型要点：chunk大小（256-1024 tokens）、overlap（10-20%）、Embedding模型（BGE/M3E/Ada）、向量库（pgvector/Milvus/Pinecone）。

Retrieval阶段：Query Embedding→ 向量检索→ 可选Rerank→ 返回Top-K。选型要点：检索方式（纯向量/混合/Hybrid）、Top-K（3-10）、Rerank模型（Cross-Encoder精度高但慢）。

Generation阶段：检索结果+Query拼Prompt→ LLM生成。关键：Prompt约束"只基于检索结果回答"、检索为空时的降级策略。

【架构类】RAG vs Fine-tuning vs Long Context，三者的选型原则？⭐⭐⭐▶

三者不是互斥的，最佳实践是组合使用。RAG管动态知识——适合频繁变化的信息，改知识库即可生效、可追溯、成本低。Fine-tuning管风格——适合内化沟通风格和领域术语理解，但知识更新需重新训练。Long Context管一次性大文档——适合单次处理超长文档，但有Lost in the Middle问题、成本随长度平方增长。选型口诀：动态知识用RAG，静态风格用微调，一次性大文档用长上下文。

【分块策略】Chunk大小怎么定？固定切分 vs 语义切分 vs 层级切分？⭐⭐▶

固定大小：按固定token数+overlap切，简单快但可能切断语义，推荐256-512 tokens。语义切分：按自然语义边界（段落/句子）切，不破坏完整性但chunk大小不均。层级切分：按文档结构层级切并保留层级关系，宽泛查询用高层级chunk、精确查询用低层级chunk。建议优先语义或层级切分，固定大小作为兜底。Overlap推荐10-20%。

【检索策略】稠密向量 vs 稀疏向量 vs 混合检索怎么选？⭐⭐⭐▶

稠密向量：Embedding映射语义空间，理解同义表达但精确匹配弱。稀疏向量：BM25关键词精确匹配强但不理解语义。混合检索（Hybrid Search）：两条路并行，RRF合并结果，两者互补。我们的实践：物流场景既有语义查询又有精确查单号，混合检索效果比纯向量好很多。通用场景优先混合检索，weight配比根据场景动态调整。

【检索策略】Query改写/转换有哪些方法？⭐⭐▶

Query扩展：LLM生成同义表达，多条检索后合并。Query重写：把模糊Query改写成明确的检索Query，适合对话中带指代的场景。HyDE：先生成假想理想文档并用其向量检索，适合极短Query但延迟高。我们只在检测到指代词/时间模糊词时才触发改写，完整Query直接检索省掉改写延迟。

【检索策略】Rerank为什么重要？Cross-Encoder vs Bi-Encoder？⭐⭐▶

Cross-Encoder：Query+候选文档拼接输入判相关性，精度最高但慢（50-150ms/对）。Bi-Encoder：各自编码后余弦相似度排序，快但精度提升有限。我们选Cross-Encoder——语音ASR转写常有误差，Cross-Encoder能更好处理语义匹配。粗召回Top-20，Rerank精排取Top-5。

【向量库选型】pgvector vs Milvus vs Pinecone vs Qdrant？⭐⭐▶

pgvector：PostgreSQL插件，零额外运维，适合百万级以内。我们早期方案。Milvus：专业向量库支持千亿级但需自建集群运维成本高。Pinecone：托管SaaS零运维。Qdrant：Rust高性能，可自托管也可云。我们最终选Viking DB（火山引擎），核心原因是和豆包生态打通好、运维托管不操心。技术选型不只看性能，还要看生态集成和团队熟悉度。

【高级RAG】什么是Agentic RAG？⭐⭐⭐▶

标准RAG是"一次检索+一次生成"的直线流程。Agentic RAG把RAG嵌入Agent推理循环——Agent自主决定是否需要二次检索、调用工具、改写Query。关键区别在于迭代和决策能力。适合多步推理查询（"这个产品去德国需要什么认证"→先查分类→再查法规→再查认证）。劣势是延迟高、成本高、调试复杂。单步简单查询用标准RAG就够了。

【高级RAG】什么是Graph RAG？和向量RAG的区别？⭐⭐▶

向量RAG做语义相似度匹配，擅长"找相关内容"但不擅长跨文档链式推理。Graph RAG把实体和关系建模为知识图谱，做图遍历查询。优势是链式推理和可解释性，但构建成本高（需要专家梳理实体关系Schema、LLM抽取需人工校验）。我们的Phase 2规划引入Graph RAG做链式推理，Drools做最终决策执行。

【高级RAG】Self-RAG和Corrective RAG是什么？⭐⭐▶

Self-RAG：模型生成时自我反思——检索结果是否相关、是否支持生成、生成内容有多少来自检索。用反思Token控制生成过程。Corrective RAG（CRAG）：检索后评估相关性，质量低时触发纠错——改写重试、WebSearch补充、或降级到模型自身知识。我们在P1容灾中的RAG降级策略和CRAG思路一致。

【评估】RAG检索质量怎么评估？指标有哪些？⭐⭐▶

检索层面：Hit Rate（是否命中）、MRR（首条命中的排序位置）、NDCG（带权重排序质量）、Recall@K（Top-K覆盖度）。计算成本低，适合日常监控。生成层面：Faithfulness（忠实度/幻觉率）、Answer Relevance（相关性）、Context Precision（上下文精确度）。可用LLM-as-a-Judge打分。我们参考了RAGAS框架的Faithfulness指标设计。

【工程实践】Embedding模型怎么选？领域微调有必要吗？⭐⭐▶

选型看MTEB/BEIR评测、向量维度、最大输入长度、语言支持。我们早期用BGE-zh，后来领域微调后命中率从72%→89%（5000对正负样本，RTX 4090 2h）。但领域微调不是必需的——通用模型hit rate > 90%就不需要额外微调。判断标准：在领域测试集上跑hit rate，低于85%才考虑微调。

【工程实践】RAG缓存策略怎么设计？⭐▶

两层缓存：检索结果缓存（Redis存Query Embedding→Top-K文档ID，TTL按知识库更新频率设5min-1h，命中率30-40%）；生成结果缓存（语义相似度匹配，命中率15-20%，仅适用静态知识场景）。对时效敏感的场景（查轨迹）只缓存检索不缓存生成，对静态知识场景（政策说明）做双层缓存。

Q5: 你觉得自己遇到的最有挑战的技术问题是什么？⭐▶

三个问题印象比较深。第一个是语音客服的TTFT优化——从15秒压到2秒。这个不是单一优化点能解决的，需要把ASR、LLM、TTS三个环节逐个压一遍，每个环节抠几百毫秒。LLM环节最费劲，Prefix Caching和KV Cache的调优花了一周多。

第二个是多租户隔离和资源复用的平衡。业务团队希望完全隔离，但完全隔离意味着资源利用率低、成本高。最后设计了"逻辑隔离+物理共享"的方案——RAG用Collection前缀隔离，记忆用user_id+project_id隔离，但底层物理存储共享。

第三个是微调数据的质量筛选。原始数据1000多条，清洗完只剩200条，筛选标准太严导致数据量不够，标准太松又影响模型质量。最后用了LLM多维度评分+人工抽检的方式，在质量和数量之间找平衡点。

智能导购 Agent — 高频面试专项

项目背景：跨越速运的To B业务中，销售团队需要快速响应客户的物流咨询（查价格、对比路线、推荐方案）。传统的推荐算法只能做固定规则的方案匹配，无法理解客户的自然语言表述和深层需求。
核心设计：三种意图（推荐/对比/通用问答）→ ReAct+Plan&Execute混合编排 → 意图Agent/工具Agent/评分Agent三Agent协作 → RAG知识库检索 → 全链路评测质检。
关键效果：AI导购转化率18.2% vs 人工19.7%（差距仅1.5个百分点，统计不显著），回复率提升23%，有效会话时长提升35%。
一-1: 智能导购Agent核心目标是什么？⭐⭐⭐▶

核心目标是用AI替代人工销售处理标准化咨询，释放销售人力聚焦高价值客户。跨越速运的To B销售每天要处理大量重复咨询——客户问价格、对比不同线路的时效和费用、询问特定物流方案。这些咨询占销售工作量的60%以上，但毛利贡献低。

具体来说三个子目标：① 准确识别客户意图（推荐/对比/通用问答），意图识别准确率从通用模型的68%提升到94%；② 从知识库中检索出最相关的产品信息并生成专业回复，RAG命中率从72%提升到89%；③ 整体转化率要达到人工销售的80%以上（实际达到18.2% vs 人工19.7%，相当于92.4%）。

一-2: 项目落地对应的业务核心指标是什么？⭐⭐⭐▶

核心指标分三层：

业务层：① 咨询转化率——从咨询到下单的转化比例，AI导购18.2% vs 人工19.7%；② 回复率——客户咨询得到有效回复的比例，提升23%；③ 有效会话时长——客户在对话中获得有效信息的时长，提升35%。

体验层：④ 客户满意度（5分制，从3.2提升到4.1）；⑤ 转人工率（AI无法处理主动转人工的比例，从优化前的25%降到12%）。

效率层：⑥ 平均响应时间（从优化前的15秒降到3秒以内）；⑦ 单会话成本（Token消耗优化60%）。

一-3: AI Agent相比传统算法的独有优势是什么？⭐⭐⭐▶

三个维度传统算法做不到：

第一，自然语言理解能力。传统推荐算法靠结构化特征（用户画像+历史行为+商品标签），但客户咨询是自然语言——"从上海到北京货物大概3吨，走空运和陆运哪个划算"。传统算法要先做意图分类→实体抽取→转结构化查询→匹配规则→返回结果，链路长且每步都有信息损失。Agent直接理解自然语言表述，一步到位。

第二，复杂推理和组合能力。客户问"帮我比较一下A和B两个方案，如果货量超过5吨有没有优惠"，传统推荐算法做不了这种带条件约束的对比推理。Agent可以通过Plan&Execute先拆解为"查A方案价格→查B方案价格→查优惠条件→用量判断→综合对比"再汇总。

第三，动态工具调用。传统算法只能查预先做好的索引表，Agent可以根据需要实时调API查价格、查时效、查库存，拿到的信息是最新的。价格变了、优惠调整了，Agent不需要重新训练，改知识库或API返回就行。

总结：传统算法适合"已知模式的批量预测"，Agent适合"未知模式的按需推理"。智能导购场景里客户问法千变万化，Agent的灵活性是传统算法替代不了的。

一-4: 只用意图层前置识别，后续交给传统推荐算法行不行？⭐⭐⭐▶

可以，而且这是我们早期尝试过的方案。实际跑下来发现两个核心问题：

第一，意图识别粒度不够。传统推荐算法需要精确的结构化输入——"发货地、目的地、货重、时效要求"。但客户不会按这个格式说话，即使做了意图分类，实体抽取环节的误差会导致推荐完全不相关。比如客户说"从深圳到北京"，意图分类正确分到"推荐"，但实体抽取漏掉了"货重30kg"，推荐算法就没办法区分零担和快递方案。

第二，条件约束和追问能力缺失。客户说"推荐一个划算的方案"，传统推荐算法只能按默认排序返回结果。但Agent可以追问——"您对时效有要求吗？大概多少公斤？"——把模糊需求逐步明确后再给精准推荐。这个追问能力是传统推荐算法不具备的。我们实测有追问和没有追问的转化率差3-4个百分点。

所以最终方案是：意图分类（轻量模型，50ms）做快速路由+Agent做深度理解和生成。意图层保证延迟和成本，Agent层保证灵活性和质量。

一-5: 只有三种意图，工程硬编码为什么不行？⭐⭐▶

如果意图只有三种（推荐/对比/通用问答），而且每种意图的回复模板固定，硬编码确实能搞定。但实际业务中三个原因导致硬编码不可行：

第一，同一种意图的输入变化无穷。"推荐"客户可以说"帮我找个方案""哪个划算""从X到Y怎么走""大概多少钱"。硬编码需要写大量条件分支，维护成本高且永远覆盖不全。微调后的模型能理解语义等价的不同表述，不需要维护匹配规则。

第二，回复质量要求自然语言而非模板拼接。硬编码拼接的回复"您的货物从XX到YY，推荐ZZ方案，价格AA元"生硬且无法覆盖异常情况。Agent生成的回复可以根据上下文调整语气、补充建议、主动推荐关联服务，客户满意度从3.2提升到4.1。

第三，场景会扩展。初始只有三种意图，上线后运营团队发现客户还会问"我的货到哪了""帮我催一下""之前推荐那个方案还能用吗"。这些新场景通过数据飞轮自动发现，补充到训练数据和状态机配置中，意图覆盖率每月提升2-3%。硬编码每加一种场景都要改代码发版，迭代周期从3天变成3周。

落地收益除了扩展性还有：运维成本下降——运营同学通过修改知识库和Prompt配置来调整回复内容，不需要开发介入；效果持续提升——数据飞轮每月自动优化，意图覆盖率持续增长。

二-1: 介绍ReAct和Plan&Execute混合架构，什么场景用Plan、什么场景用ReAct？⭐⭐⭐▶

ReAct是"边想边做"——模型每推理一步就决定是否调用工具，适合需要不断根据新信息调整决策的场景。Plan&Execute是"先想好再做"——先规划出完整的执行步骤列表，再按步骤执行，适合步骤明确的复杂任务。

决策逻辑看两个维度：步骤确定性和环境反馈频率。如果步骤确定且有最优解（比如"查价格→对比→推荐"），走Plan&Execute。如果需要根据中间结果动态调整（比如客户问"等等我换个条件"，前面的Plan需要重新做），走ReAct。

我们的混合架构设计：先走Plan做初步规划，执行过程中如发现客户修改条件或检索结果不符合预期，触发RePlan重新规划而不是死板执行原Plan。这个设计解决了Plan&Execute不够灵活和ReAct容易跑偏两头的问题。

二-2: 工具调用链路中如何保证鲁棒性？⭐⭐⭐▶

三层防护：第一层，超时+重试+熔断。每个Tool调用设超时（默认3s），失败自动重试3次（指数退避1s/2s/4s），连续5次触发熔断走降级。降级不是报错，是根据已有信息做"部分推荐"——比如查实时价格失败了，用缓存的价格数据+提示"价格为近期参考值"。

第二层，输出校验。Tool返回的数据用Pydantic Schema校验，类型不对、必填字段缺失直接丢弃不走LLM推理，防止脏数据污染模型。比如运价查询返回的金额字段是字符串"五百"而不是数字500，Schema校验拦截并触发重新查询。

第三层，幻觉约束。LLM生成的回复必须引用Tool返回的数据来源，Prompt明确写"不允许编造Tool未返回的信息"。评测环节有专门的Faithfulness指标检测幻觉，季度内从5%压到1%以下。同时结合Drools规则引擎做硬约束，比如推荐方案的报价超出知识库中的价格区间则拦截。

二-3: 三个Agent如何分工？输出格式？⭐⭐▶

意图Agent：判断客户query属于推荐/对比/通用问答三种意图之一，同时抽取关键实体（发货地、目的地、货重、时效）。输出结构化JSON：{intent: "recommend", entities: {from: "上海", to: "北京", weight: "3t"}}。

工具Agent：维护所有可用Tool的列表和调用方式，根据意图Agent的输出和当前上下文决定调用哪些Tool、调用顺序、参数提取。输出Tool调用链和参数。单独拆分工具Agent的原因见下题。

评分Agent：对工具Agent返回的多组方案做综合评分（价格、时效、服务质量等多维度加权），输出排序后的推荐列表+评分理由。评分规则写在Prompt里，但最终决策锚点（哪个维度权重高）由运营团队在后台配置，不需要改代码。

二-4: 为什么单独拆分工具Agent？直接放主Prompt不行吗？⭐⭐⭐▶

早期就是把所有Tool定义直接放在主Agent的System Prompt里。随着Tool数量增加（从5个涨到20+），两个问题暴露了：

第一，System Prompt过长导致注意力稀释。Tool定义占了60%的token预算，主Agent处理意图判断和回复生成时注意力被Tool描述分散，意图准确率下降了3-4%。而且每次调用LLM不管用不用Tool都要把所有Tool定义过一遍，浪费token。

第二，Tool选择逻辑和业务逻辑耦合。比如"查价格"这个Tool在不同场景下的调用参数不一样——推荐场景用包裹总重，对比场景用单票重量。主Agent既要理解业务场景又要选择Tool参数，一个改动要同步改多个Prompt。

拆出工具Agent后的收益：① 主Agent的System Prompt token减少40%，意图准确率回升且成本下降；② 工具Agent可以独立维护Tool的调用逻辑和参数映射关系，新增一个Tool只需要在工具Agent侧注册，不需要改其他Agent；③ 工具Agent可以做Tool调用的重试、降级、熔断等基础设施逻辑，主Agent不需要关心。

二-5: Skill设计模式不需要独立工具Agent，你们为什么还要做？⭐⭐▶

MCP的Skill模式（Tool Discovery）确实能解决"Agent自动发现可用Tool"的问题，不需要自己开发工具Agent。但我们的场景有一个关键差异：工具调用不是独立的一步，而是需要多轮协商的持续过程。

比如客户说"从上海到北京，3吨货，帮我比较一下空运和陆运"。工具Agent需要：①先调价格API查两种方案的基础价格；②发现空运超过2吨有折扣，需要再调折扣API确认具体折扣；③陆运有特殊货品限制，需要调限制API确认3吨是否超限。这涉及多轮工具调用的依赖协调——下一步调什么取决于上一步返回了什么。如果只是把Tool列表塞给主Agent，主Agent的推理负担太重。

工具Agent的另一个价值是参数预填充。同一个Tool在不同场景下的默认参数不同，工具Agent可以根据当前场景预填充参数，减少LLM的推理轮数。比如推荐场景默认按价格排序，对比场景默认按时效排序。这些预填充规则写在工具Agent的配置里，不需要主Agent理解。

三-1: 知识库文档切片怎么做？落地遇到什么问题？怎么持续优化？⭐⭐⭐▶

我们的切片策略分三层：第一层按文档类型——Markdown格式按标题层级##/###切，保持层级关系做结构化解构；纯文本按段落+语义边界（句子结束符+主题转换检测）切；表格每行一个chunk+上下文表头；PDF用版面分析区分文本区和表格区分别处理。切片大小控制在256-512 tokens。

落地遇到的最大问题是边界截断导致语义丢失。比如一个关于"空运危险品"的文档，前一个chunk讲"空运的限制条件"，后一个chunk讲"危险品的包装要求"，中间被切断了。客户问"空运危险品有什么要求"，检索只能召回其中一个chunk，信息不完整。解决方案是加overlap策略（chunk结尾重叠2-3句）和层级递归检索（先查粗粒度chunk定位文档，再查细粒度chunk定位具体内容）。

持续优化分三步：① 每周分析badcase中被标记为"RAG不准"的case，看是切片问题还是embedding问题；② 如果是切片问题，调整该类型文档的切片策略（比如加大overlap、改用语义边界替代固定长度）；③ A/B测试新策略和旧策略在检索hit rate上的差异。每月切片策略迭代2-3次。

三-2: 不同文档的差异化切片策略？⭐⭐▶

三类典型文档的处理：长文对话（客服对话记录）——按时间窗口30分钟+Embedding语义相似度切分，超过30分钟或语义不相关的拆成独立对话。不是固定长度切，避免切断同一个话题的对话流。

产品文档（价格表/服务说明）——按Markdown标题层级切分，保留层级树结构。检索时先匹配高标题（如"价格说明→空运"），再匹配具体内容。客户问"空运价格"直接定位到"价格说明→空运"子树的chunk，比全文检索精度高很多。

表格数据（运费对比表/时效对照表）——每行单独作为一个chunk，但保留表头作为上下文前缀嵌入。比如一行数据是"上海→北京, 3吨, 空运, 5000元"，实际存入向量库的是"运费对比表 | 出发地:上海 | 目的地:北京 | 重量:3吨 | 方式:空运 | 价格:5000元"。这样检索"上海到北京空运价格"时embedding相似度更高。

三-3: 召回命中率从70%提升到95%，指标怎么定义的？Top几？⭐⭐⭐▶

我们的召回命中率定义为Hit Rate@5——Top-5检索结果中是否包含至少一个正确答案。这是RAG场景最实用的指标，因为LLM的上下文窗口通常能容纳5-10个chunk，只要Top-5里有一个对的，LLM就有机会生成正确答案。

不选Top-1的原因是客服场景的查询经常有多个可能的答案来源（比如同一个价格信息可能存在于"价格表"和"历史报价"两个文档中）。不选Top-10是方便后续rerank环节有足够的候选集。

另外监控MRR（Mean Reciprocal Rank）——正确答案在排序中的平均位置。MRR从0.45提升到0.82，说明不仅命中率提高了，命中的位置也更靠前了。这对LLM生成质量有直接影响——正确答案排在越前面，LLM输入中相关信息的占比越高。

三-4: 从70%优化到95%做了哪些优化动作？⭐⭐⭐▶

六个优化动作，按收益排序：

① Embedding领域微调（+12%）。通用Embedding模型对物流术语"分拨中心""干线运输""改配"理解不够，用5000对正负样本做了领域微调。这是最有效的单一优化。

② 混合检索Hybrid Search（+6%）。纯向量检索+BM25关键词检索，Reciprocal Rank Fusion合并结果。精准匹配运单号、价格数字时BM25非常有效。

③ Rerank精排（+3%）。粗召回Top-20→Cross-Encoder精排取Top-5。Cross-Encoder精度高，ASR误差导致的噪声能过滤掉大部分。

④ Query改写（+2%）。检测到指代"那个""上次""之前说的"时做LLM改写，消除歧义。只对指代模糊的query触发，完整query不改写省延迟。

⑤ 切片策略优化（+1%）。从固定长度切改为语义边界+层级切分，减少边界截断导致的信息丢失。

⑥ Metadata过滤（+1%）。根据客户画像（VIP等级、所在地区）过滤不相关的知识库集合，减少检索噪声。VIP客户能看到内部处理进度，普通客户只看到公开信息。

三-5: 切片/意图标注粒度过细或过粗分别有什么问题？⭐⭐▶

切片粒度过细（<100 tokens）：单个chunk信息不完整，LLM无法基于碎片化信息生成完整回答。而且chunk数量暴增导致检索延迟上升。极端情况一个文档切成几百个chunk，Top-5召回的信息可能全是碎片，LLM拼不回来。

切片粒度过粗（>1000 tokens）：一个chunk包含多个主题，检索命中时无法精确定位到客户关心的那一段。而且chunk过大导致LLM输入token浪费——只需要其中一段信息但要把整个大chunk传给LLM，增加延迟和成本。

意图标注粒度过细（50种+意图）：不同意图之间的边界模糊，分类模型准确率下降。而且长尾意图的训练数据稀疏，效果不可靠。我们压到12种核心意图后准确率从68%提到94%。

意图标注粒度过粗（3-5种意图）：多种不同的业务场景被归为同一意图，后续的处理流程无法差异化。比如"查轨迹"和"查时效"归为"查询"，但查轨迹需要调运单API，查时效需要调线路API，流程完全不同。

四-1: 全链路评价和质检体系如何搭建？⭐⭐⭐▶

全链路分三段评价：意图识别→RAG召回→生成质量，每段有独立的指标和评测方式。

意图识别层：用人工标注的测试集（2000条，覆盖12种意图）定期跑分类准确率，监控点设在CI/CD流水线中每次模型/Prompt更新时自动触发。指标：意图准确率（目标≥90%）、实体抽取F1（目标≥85%）。

RAG召回层：离线评测用标注的Query-Chunk正负样本对算Hit Rate@5和MRR。线上监控用间接信号——如果LLM回复中引用了知识库内容但客户继续追问（"还有吗""再说详细点"），说明召回可能不完整。

生成质量层：三层评估——① 自动指标（BLEU/ROUGE做快速排雷，检测明显异常）；② LLM-as-a-Judge（用专门的评估模型对回复的准确性/完整性/合规性打分，每月跑一次全量）；③ 人工盲评（3名评估员各评50个case，Cohen's Kappa≥0.6确保一致性）。

四-2: 评测用什么模型？输入数据是什么？⭐⭐⭐▶

评测模型用的是GPT-4或豆包pro（两者做交叉验证，结果不一致时取较低分），而不是我们自己的微调模型。原因是要避免评测偏差——用自己的模型评测自己会产生"自我感觉良好"的假象。

输入数据分三部分：① 原始Query（客户说的话）；② Agent的完整回复（待评测的对象）；③ 评测上下文（包括检索到的知识库chunk、调用的Tool返回结果、意图分类结果）。评测模型不是只看回复本身，而是对比"回复"和"检索结果"的一致性来判断是否存在幻觉。

给评测模型的Prompt包含评分标准和示例，要求输出结构化JSON：{faithfulness_score: 0-5, completeness_score: 0-5, issues: ["问题描述", ...], verdict: "pass"|"review"|"fail"}。

四-3: 从系统日志筛选异常case，谁先判定？⭐⭐▶

机器先筛，人工确认。三个自动触发信号：① 客户满意度评分<3分（IVR调查）；② 对话轮数>10轮（说明模型没理解或没解决）；③ 客户主动说"转人工""找你们领导"。这三个信号的日志会自动打上badcase标签进入待审查队列。

人工确认的流程：运营同事每天花30分钟审这批badcase（约50-80条），用LLM预分类打上初步标签（意图缺失/RAG不准/幻觉/流程bug/其他），运营只需要确认或修正。预分类准确率约80%，能省掉大部分重复劳动。

确认后的badcase进入不同的优化队列：意图缺失→补充训练数据；RAG不准→更新知识库或调整切片策略；幻觉→优化Prompt约束+补充负样本到评测集。每个优化动作完成后走回归测试→5%灰度→全量上线。

四-4: 评测大模型是否挂载知识库？知识库存什么？⭐⭐▶

评测大模型不挂载知识库。评测的输入中已经包含了Agent检索到的知识库chunk，评测模型只需要对比"Agent回复"和"给定的知识库chunk"的一致性，不需要自己去知识库搜索。如果评测模型也挂知识库，它可能用自己的检索结果覆盖Agent的检索结果，导致评测失准——Agent实际没用到某条知识但评测模型自己查到了，误判Agent回复正确。

但评测模型挂载了历史badcase库作为few-shot示例。Prompt里会带3-5条历史badcase（"之前出现过的情况：客户问X，Agent回了Y，但正确的应该是Z"），让评测模型知道"什么样的回复算badcase"。这个badcase库每月更新，从已确认的badcase中采样。

四-5: 评测环节打分标准是什么？⭐⭐⭐▶

三个维度各0-5分：

准确率（Faithfulness）——回复中的每一条事实是否能从检索结果或Tool返回数据中找到对应来源。无中生有的事实扣分，引用正确的加分。阈值：4分以下标记为"review"。

完整性（Completeness）——回复是否覆盖了客户Query中的所有需求点。客户同时问了价格和时效，回复只说了价格没提时效，扣分。阈值：3分以下标记为"fail"。

规范性（Compliance）——回复是否符合业务规范。比如价格报价必须包含"有效期"提示、推荐方案必须包含"是否包含税费"说明、不允许使用"一定""肯定"等绝对化表述。规则来源于业务SOP，用Drools规则引擎做硬约束+LLM做软检查。

最终判定规则：三个维度都≥4分 → pass；任一维度3分 → review（人工确认）；任一维度≤2分 → fail（阻断发布）。

四-6: 全新未知业务场景，评测模型识别不出异常case，问题如何闭环？⭐⭐⭐▶

这是最棘手的情况——评测模型没见过的新场景，它不知道什么是"对"什么是"错"。我们的解法是多层兜底+快速反馈闭环：

第一层，规则兜底。即使评测模型判断不出异常，业务层面的硬规则（Drools）仍然在运行。比如报价超过历史价格区间的200%、推荐了禁运品类、回复中漏掉了必填字段（如"是否含税"），规则引擎会拦截并标记需人工复核。

第二层，线上指标监控。新场景上线后24小时内重点监控业务指标——转人工率、客户满意度、对话轮数。如果转人工率突然从12%飙到30%，说明新场景的Agent处理有问题，自动触发降级（切回人工兜底）。这不是评测模型发现的问题，是业务指标发现的。

第三层，快速反馈闭环。一旦通过上述任意渠道发现问题，新场景的case进入badcase队列，运营24小时内完成标注，评测集3天内补充该场景的测试case。这个case加入后，下一次评测模型就能识别同类问题了。核心是闭环速度——从发现到补充到评测集不超过72小时。

至于"评测模型自身识别不出"的问题，我们的经验是定期（每月）用线上样本刷新评测集，用真实badcase替代老case，保证评测模型见过的场景覆盖度不低于80%。如果覆盖度低于80%，优先补充新场景的标注case。
